# Security review record for the v1 gate (A3.5, #295)

Date of the review: 2026-11-25. Tip reviewed: `origin/main` at bcdf874 (after #401) plus the dependency fix in this PR.

This is the review the gate asked for: what changed in the threat model since Phase 2, where the credential and consent boundaries sit now, what the sandbox host is (and is not), what leaves the machine over OTLP, and how the evaluation and comparison code treats the files it reads. `docs/SECURITY.md` stays the threat table with a test under every row; this page is the delta and the verdict. I read the code and the tests and I ran the supply-chain checks. I did not run any vendor CLI for this review, and nothing here is a third-party audit.

The short version: one real finding (four known advisories in the lock file) is fixed in this PR. The rest I could not close inside this issue, and each one is listed below with where it goes. I can say there is no credential-harvesting path in the code that exists today, but only because the code that would use most of these boundaries at run time is not wired into a command yet (see "What the boundaries do not yet protect").

## Supply chain (spec 10.2: pinned hashes, signed releases, provenance, revocation)

I ran these on MARS in the `aibus-gate:1.89` image, which has neither tool baked in, so the script downloads the release binaries for the run (`cargo-deny` 0.22.1, `cargo-audit` 0.23.0, both x86_64 musl) and throws them away with the container.

| Check | Command | Result before this PR | Result after |
|---|---|---|---|
| Advisories | `cargo deny --locked check` (root `deny.toml`) | failed: RUSTSEC-2026-0566, -0569, -0571 (`wasmtime` 36.0.20, pinned `=36.0.20` by `aibus-extension`) and RUSTSEC-2026-0592 (`url` 2.5.8, through `reqwest`, `rmcp`, `tower-http`, `wiremock`) | SUPPLY_AFTER |
| Licences, bans, sources | same run | ok (licences ok, bans ok, sources ok) | ok |
| RustSec | `cargo audit` 0.23.0 | the same four vulnerabilities, plus four unmaintained notices | SUPPLY_AUDIT_AFTER |
| Lock floor, offline | `cargo test -p aibus-testkit --test workspace the_lock_holds_no_version_with_a_known_advisory_fix_missed` | red (`url` 2.5.8 is below 2.5.9) | green |

The four vulnerabilities were real, so I fixed them: `aibus-extension` now pins `wasmtime` `=36.0.21` (the fix on the 36.0.x line that the crate's comment already chose, so the MSRV and the feature set do not change) and `url` is at 2.5.9 through `cargo update -p url --precise 2.5.9`. `smol_str` 0.3.2 and `proptest` 1.11 are still pinned (docs/BUILD.md). The wasmtime advisories reach `aibus` only through the `wasm` feature of `aibus-extension`, which is off by default, and `wasmtime-wasi` and `wasmtime-wasi-http` are not compiled (no WASI), so the practical exposure was small. I did not weigh it that way when deciding: a known advisory in the lock is a gate failure either way.

The test I added reads `Cargo.lock` and fails when `wasmtime` or `url` falls below the fixed version. It exists because a lock merge that takes an old side is exactly how this comes back, and `cargo deny` needs the network to say so. It checks two names and goes stale when a floor is no longer the interesting one; delete a row when the next bump makes it moot.

Still open from the same runs:

* **Unmaintained crates, no fix available:** `chrono` 0.4.45 (RUSTSEC-2026-0543, from `rmcp`), `zbus_names` 3.0.0, `zvariant` 4.2.0, `zvariant_derive` 4.2.0 (RUSTSEC-2026-0370, -0371, -0372, the Linux Secret Service path of `keyring`). `cargo deny` reports them and does not fail the run; `deny.toml` has `unmaintained = "all"`, so a later release of `cargo-deny` or a changed policy could turn them into a failure. They go to docs/DEFERRED.md. Nothing in them is a known vulnerability today.
* **The causl crate's own lock** (`crates/aibus-graph-causl`, outside the workspace, private git source) was not checked: the gate image cannot reach `git.opsite.ca`. Unverified.
* **Signed releases and revocation** are not a code question here: `release.yml` and the local release gate (#221, #222, #223, #225) carry the attestation, and docs/RELEASE.md covers it. I did not re-run the release attestation for this review.
* **Extension provenance and revocation** (what spec 10.2 names for extensions) is built and tested: `aibus-extension/tests/registry.rs` (hash mismatch, signature, publisher allowlist, revocation by version, hash or whole id, a replayed older index), `store.rs` (every resolve re-hashes, quarantine, pin, rollback, no downgrade), `key_scope.rs` (a signing key is bound to the ids it may sign). It is a local registry directory, with no network service, so "revocation" means the list inside the registry the user points at, plus the user's own policy file.

## Credential and consent boundaries

* **aibus-owned credentials** (API keys and OAuth tokens for the providers aibus calls itself, OpenRouter's included): keychain only, `Secret<T>`, the redactor, and the checks listed in docs/SECURITY.md, which this review did not reopen. OpenRouter is the one direct provider in the spec, and its key stays in the keychain; `account revoke` removes the keychain entry and says the key is still valid at OpenRouter until it is deleted there.
* **Vendor-owned credentials** (Claude Code, Codex, Gemini, and the rest): aibus runs `auth status` style commands when a manifest declares them and never reads the result's token, and never starts a login of its own. The spike found `claude auth status --json` carries an email and an organisation name, so those have to be redacted wherever the status is shown (A1.1, evidence.md).
* **Subscription sign-in for Claude Code** stays an owner decision (docs/spikes/A1.1-claude-code/terms-gate.md, owner question 1, still open). Until it is answered the documentation must not advertise it.
* **Consent** exists as a checked record (`workflow::handoff`), and as a rule in Jev (an unapproved OpenRouter candidate is skipped). It does not yet exist as a prompt. The live pair (Codex then Claude Code) is an ignored test whose consent is an environment variable standing in for a person, and its record says so.

## What the boundaries do not yet protect

This is the part that decides the verdict. Several of the boundaries above are libraries that no command calls yet, so they are tested but not in force for a user:

* `aibus-otel` is called only by its own tests. There is no config key and no command that builds a `Destination`. "Off by default" is true because nothing turns it on.
* The scheduler (#288) and the durable run (#289) are not behind `aibus workflow run`, the TUI or MCP; the chain runner still runs workflows. So the approval gates, the handoff consent, the OpenRouter approval and the per-attempt worktree review are not yet on the path a user's run takes. D-359 and D-360 name the guard that has to be added when the scheduler is wired (pass the resolved account provider; persist the spent set; set the record store's modes).
* No product command starts a vendor CLI through `aibus-supervisor` yet. `aibus extensions test` replays fixtures through the conformance runner and starts nothing; the supervisor runs real CLIs only in the ignored live tests (`handoff_live.rs`, `live_reference`). `aibus-tap` reads what a session the user already started sends, and starts nothing either.

So "zero known credential-harvesting paths and no unapproved provider embedding paths" holds for the code that exists. It is not yet a statement about a running product, and I will not word it as one.

## OTLP: what leaves the machine

* **Whether:** only with a `Destination` a caller builds. None is built anywhere in the product today.
* **What:** the trace as an OTLP/JSON traces request: span names are fixed strings (`aibus.workflow.run`, `aibus.attempt`, `aibus.agent`, `aibus.delegation`, `aibus.tool`); tool name, agent role and provider extension are attributes; usage with its quality and an unknown value sent without a number; prompt and workflow revision ids on the resource, never prompt text; route decisions, approvals, artifacts, gaps and warnings as events. Message chunks are not exported.
* **Still in it, even with redaction:** file paths, agent names and anything a tool name carries. The redactor is best effort for a secret nobody registered.
* **Transport:** reqwest with the system roots, no redirects, the caller's timeout. The endpoint is whatever string is handed in: a plain `http://` endpoint to a public address is accepted and a header such as a Langfuse basic-auth value would cross the network in the clear (F2).
* **Checked against a real collector:** `otel/opentelemetry-collector:0.116.1` on 2026-11-25, in a throw-away network (docs/OTEL.md). Langfuse was never run.

## Evaluation and comparison data

* **Eval results** hold names, counts, ids and metrics, plus the case's `privacy` policy; no payload is stored or shown. A result is bound to its run and revision (`a_run_at_another_revision_is_refused`, `a_result_of_another_run_or_of_another_version_is_never_taken_for_the_run`), so a result file from another run cannot vouch for this one. A model judge needs the suite to allow it (`scores_are_secondary_and_a_model_judge_needs_the_suite_to_allow_it`). Nothing sends a result anywhere.
* **Compare and inspect** read local trace and result files. The CLI refuses a FIFO as a result file before opening it, an overflowing size is a gap and never a panic, and hostile text (bidi, C1 and escape characters in a trace, a usage metric, a parse error or an environment value) is cleaned before it is drawn or serialised (`a_hostile_trace_cannot_put_an_escape_sequence_in_the_comparison`, `runs_inspect_json_writes_no_bidi_or_c1_character_from_a_hostile_usage_metric`, `runs_compare_refuses_a_fifo_as_a_result_file_without_waiting_for_a_writer`). A prompt or an output is shown only when the run kept it, which needs an explicit payload policy.
* **Suggestions** carry agent ids and tool names straight from the trace, so a renderer other than the two that exist has to escape them (docs/DEFERRED.md, A3.3).
* **Fixture repositories:** the suite names ten repository paths that are not in the tree, and no runner exists. When one is written it has to confine `fixture.repository` to the checkout root and refuse a `commit` that starts with a dash. That is a precondition for the runner, not a finding about today's code.
