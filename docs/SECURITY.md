# Security

This is where the threat table of `docs/spec/09-security.md` section 10 meets the tests. Every row names the test (or the CI job) that exercises its mitigation, so a row with nothing under it is a bug in this file. I wrote the tests under `crates/aibus-core/tests/security/` for C2.1, and the older ones are listed by name so they are easy to find from here.

The short version of what aibus promises: the tool policy is a real boundary at the aibus process, and nothing more. A command that starts through `bash` has your rights unless you turn the optional sandbox on (below). `--permission-mode bypass` says so in its `--help`.

## The redactor

The pattern half is best effort, and I keep it honest with two corpora. `aibus-core/tests/redact.rs` has a positive and a negative line for every pattern. `security/redaction.rs` runs the redactor over the recorded provider cassettes of both provider crates (it must leave all of them as they are) and over `fixtures/redact/provider-errors.toml`, which holds error bodies in the shapes providers and gateways echo a credential back in.

That second file is what found three gaps, now closed: OpenAI project, service-account and admin keys (`sk-proj-...`, the hyphen stopped the old `openai-key` pattern), Google API keys in a URL (`AIza...`), and gateways that echo a header or query field (`x-api-key`, `api_key=`). When a fuzz run or a real incident finds another, the order is: add the body to `provider-errors.toml`, add the pattern to `patterns.toml`, add the positive and negative lines to `redact.rs`.

Every credential kind the code can hold is listed once in `aibus_testkit::CREDENTIAL_KINDS` (API keys, OAuth access and refresh tokens, the AWS key id, secret and session token, a Bedrock API key, Google access tokens from `gcloud`, Gemini and OpenRouter keys, the MCP HTTP bearer), with the pattern that knows its shape or none. `provider-errors.toml` has a row for each (`security/redaction.rs::every_credential_kind_the_code_can_hold_has_a_row_and_the_right_layer_catches_it`; a row for a kind without a pattern lists it under `registered`, and `::every_row_turns_red_when_the_redactor_misses_its_secret` shows a blind redactor turns every row red and that `registered` is load-bearing). `capture_logs` and `xdg_temp` forbid all of them, `persist.rs::every_credential_kind_stays_out_of_the_transcript_msgs_and_every_file` plants them in a transcript, and `mcp_security.rs::no_secret_leaves_over_stdio` sends the pattern-shaped ones over stdio and greps stdout, stderr and the audit file. The two shapes this found missing, Google access tokens (`ya29.`) and OpenRouter keys (`sk-or-v1-`), now have patterns.

## Fuzzing

`fuzz/` is a `cargo-fuzz` workspace of its own (nightly, libFuzzer) with five targets: `agent_def` (`agent::def::parse`), `handoff` (handoff YAML), `redactor` (`Redactor`, including that no registered key or key-shaped token survives) `tool_pattern` (the `ToolPattern` text form, the specifier glob, the bash splitter and the deny list) and `commands_send` (the dashboard's `send()` over a random line and a random session, with every documented command as a seed). The bodies of the first four are in `fuzz/checks.rs`, and `security/fuzz.rs` runs the same functions over every file in `fuzz/corpus/<target>/` and `fixtures/fuzz/<target>/` on every push, so the corpus is also a regression suite. The body of `commands_send` is in `fuzz/commands_checks.rs`, and `crates/aibus-tui/tests/security_commands.rs` replays its corpus the same way, because the dashboard crate is not something the core tests can depend on.

The `.aibus` bundle reader has no cargo-fuzz target yet; `security/bundles.rs::random_and_mutated_tar_bytes_never_panic_and_never_write` runs it on every push over 32 000 inputs from a fixed seed (random bytes, valid bundles with bytes flipped, cut or spliced), and checks that `read` never panics and that `install` never leaves a file behind unless the bundle read clean.

A crash from a fuzz run goes into `fixtures/fuzz/<target>/` with a descriptive name, plus a plain unit test next to the code that was wrong. The first one was found while setting this up: `ShellDeny::hit` sliced one byte past a space, which panics on a two-byte space such as U+00A0 (`fixtures/fuzz/tool_pattern/deny-hit-slices-inside-a-multibyte-space`).

Run it in a container, never on a host. The script installs nightly and `cargo-fuzz` itself:

```
docker run --rm -v "$PWD":/work -w /work rust:1.89 sh tools/fuzz.sh 60
```

The local run on MARS is the real gate. `.github/workflows/fuzz.yml` is the same thing, manual only (120 seconds per target, crash artifacts uploaded).

## Identity and logins

aibus never sends another product's client id, user agent, fingerprint, attestation or billing header, and never claims to be a first-party client. A vendor login lands in aibus only when the vendor documents a flow for third-party applications. A subscription plan that is only reachable by posing as the vendor's own CLI is out, whatever the demand. Every request aibus makes says `aibus/<version>`.

The two login flows (`crates/aibus/src/oauth/`) keep to the same rules as a key. The PKCE verifier, the state, the authorization code and every token live in memory only: tokens are `Secret`, the verifier is never printed or put in a URL, and an error from the token endpoint names the status and the server's `error` code and nothing else from the body. The loopback listener binds 127.0.0.1 only, accepts one exact path, requires a loopback `Host` header and (when the server echoes it) the matching `state`, closes after the first good request and gives up after five minutes. Tests: `crates/aibus/src/oauth/tests.rs` (listener, state, path, Host, timeout, device responses), `crates/aibus/src/account/tests.rs` (the keychain and file grep for the key and both tokens), `crates/aibus-core/tests/oauth_single_flight.rs`.

## Providers, the gcloud subprocess and the catalog

Three more things about providers that are not a login.

* **`gcloud`.** For a Vertex account with `auth = { gcloud = true }`, aibus runs `gcloud auth print-access-token` when `GOOGLE_OAUTH_ACCESS_TOKEN` is not set. It is found on `PATH`, started with an argument list and no shell, killed after 10 seconds, with its stderr dropped. Its output is treated as a secret: it is cached for 50 minutes in memory under the account's name and never written to disk or to a log, and an error says that `gcloud` failed without repeating what it printed. Tests: `aibus/src/gcloud.rs::the_token_comes_from_gcloud_once_and_is_then_cached_under_the_account`, `::a_gcloud_that_fails_is_an_auth_error_that_repeats_nothing_gcloud_said`.
* **The model catalog.** aibus fetches no third-party catalog at run time. The built-in tables are `catalog/*.json` in the repository, included in the binary; `catalog-sync` reads a snapshot I save by hand and never fetches, and prices change only through a reviewed pull request. The only list that comes over the network is a provider's own model list, refreshed with that account's key into `~/.cache/aibus/models/`.
* **Plain http.** A `base_url` of `http://` is allowed for this machine and for private networks (a local model server is the normal case) and draws a warning anywhere else, because a key sent there can be read on the way. It is a warning and not an error, since a lab VPN is a legitimate setup.

## The optional shell sandbox

Off by default, and never the default in v1. Turn it on in `config.toml` or `.aibus/settings.toml`:

```toml
[tools]
sandbox = "bwrap"          # or "sandbox-exec" on macOS, or "none"
sandbox_network = false    # default true; false cuts the network inside the sandbox
```

`bash` then runs inside it with the filesystem read-only except the project (or the run's worktree) and `$TMPDIR`, and your home directory is not visible. Hooks and MCP servers are not sandboxed: they are commands you configured yourself. If the program for the configured kind is not on `PATH`, `bash` refuses the call, it does not run unsandboxed, and `aibus doctor` fails the `shell sandbox` check. `aibus doctor` prints `shell sandbox: none` or the active one (`bwrap`, `bwrap, network off`).

The `bwrap` profile is tested in a container (`security/sandbox.rs`, with `AIBUS_REQUIRE_SANDBOX=1` so the test fails instead of skipping). The `sandbox-exec` profile is written but I have not run it: nothing in this repository's gates runs on macOS, so the same test is compiled for macOS and has to be run there by hand.
