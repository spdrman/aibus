# B1.5 Phase 1 gate: spike review, performance baseline and the ADR-B-001 decision (#308)

This is the gate for Phase 1 of EPIC B (#303). I reviewed B1.1 to B1.4 (#304 to #307, all merged)
against the Phase 1 exit gate, took the baseline I could take, and recorded the decision on
ADR-B-001. A reviewer who didn't build the spike reads this before Phase 2 (#309 to #313) opens.

Every number below has a command that repeats it, or it says it is unverified.

## Decision: GO-WITH-CONDITIONS

ADR-B-001 stands: Tauri 2 shell, React and TypeScript front end, the Rust core and the Ratatui TUI
stay, no egui. A panel of ten roles argued it adversarially (the Tauri platform, WKWebView, React
performance, Rust IPC, security, QA, delivery, an egui advocate, a NO-GO devil's advocate and a
measurement skeptic) and 8 of 10 signed the consensus below. The record is the comment on #308.

Nothing I measured triggers the "revisit if" clause ("measured platform/webview constraints prevent
achieving agreed responsiveness targets"). The only slow numbers are on the Rust side and come from
how the bridge reads the trace, which egui would inherit unchanged. But the webview side is
unverified, so this is a GO because nothing contradicts it, not because it is proven.

### Conditions

1. **Blocks opening Phase 2: macOS.** The owner runs [VERIFY-MACOS.md](VERIFY-MACOS.md) and records the
   result in B1.1's doc. B1.1 itself says GO is not confirmed without it.
2. **Blocks opening Phase 2: independent review.** A reviewer who didn't build the spike signs off on
   this PR (the owner's rule on #308).
3. **Blocks opening Phase 2: numeric targets.** Write responsiveness targets (first render, selection
   latency, live-append latency) as targets, not guarantees. Without numbers the revisit clause can
   never fire. I didn't invent any here.
4. **#310:** wire `aibus_bridge` into `src-tauri` and retire the spike's two commands. Fix the
   per-call re-read of the trace (see the numbers). Send deltas by cursor, not a whole projection
   per step.
5. **#310, first deliverable:** the real-webview measurement at medium and large comes before anything else in #310, and before #309 or #311 build graph or timeline components. A bounded visible graph (collapse, virtualise or React Flow), picked from a real-webview
   measurement at medium and large. The fixed-pixel SVG doesn't go to 49,000 tool nodes.
6. **#311:** a virtualised timeline, and never the 17.6 MB projection in one reply.
7. **#312:** every new command granted by name, no shell, fs or http plugin, launch arguments bounded,
   and the credential-boundary test extended to the bridge DTOs.
8. **#313:** Playwright against the real webview (through `xdg-pw-lock.sh`), keyboard access to graph
   nodes, count-based smoke tests only in CI.
9. **#309:** uses the graph component that #310 picks (condition 5), no second graph stack.
10. **Revisit trigger (#310):** if the targets from condition 3 fail on WKWebView or WebKitGTK after
    one targeted optimisation pass, reopen the ADR with egui scoped to the graph panel only.

Alternatives that lost: NO-GO until the webview is measured at scale (it needs the bridge wiring and
a bounded graph, which are Phase 2 work, and conditions 1 to 3 and 10 give the same protection), and
a hybrid egui graph panel now (no measured need, and it throws away the merged shared-ui, bridge and
shell work). Dissent: the NO-GO role would only sign if condition 5's measurement blocked Phase 2
instead of living in #310; the skeptic signs with the note that the datasets clone one fixture shape.

## Datasets

All three come from the recorded spike trace with a fixed seed (`0x308308308`), so any machine gets the
same events. They live in code, not in the repo as megabytes of JSON:
`crates/aibus-bridge/tests/phase1_gate_308.rs`.

| Dataset | Events | Agents | Tool nodes | `events.jsonl` |
|---|---|---|---|---|
| small | 29 (the recorded `07-deleg`) | 3 | 2 | n/a |
| medium | 10,000 | 50 | 4,900 | 6.7 MB |
| large | 100,000 | 500 | 49,000 | 67 MB |

"500 nodes" in the issue I read as 500 agents. The shape is the spike's: a lead delegates to each child,
a hook confirms every child, then random tool start and complete pairs on random agents, then stops.
Real runs with deeper nesting or different fan-out may behave differently (the generator clones one shape).

CI-compatible smoke tests (counts only, no timing, run in the normal `cargo test -p aibus-bridge`):
small is the recorded trace (3 agents, 2 edges, 2 tools), medium and large have exactly the agent,
edge, tool and timeline-row counts above, every child edge is cross-checked, the same seed gives the
same events, and a cursor walk over medium is 20 batches of at most 500 that deliver every event once.

## Baseline

What the probe times is the Rust side of the bridge (`aibus_bridge::handle`), release build. It does
not time a webview. Command: `tools/phase1-gate/probe.sh` (needs `DH` and `BENCH_QUEUE`, see the
header). Raw output: [data/b1.5-probe-mercury-2026-11-25.log](data/b1.5-probe-mercury-2026-11-25.log).

Host facts for the Mercury MacBook, read over ssh with `sysctl -n machdep.cpu.brand_string hw.ncpu hw.memsize; sw_vers -productVersion` (Apple M1, 8, 17179869184 bytes, 26.4.1); the VM figures come from the raw log.

Host: MERCURY, run 2026-11-25 through the bench queue as job `s308-probe`. Apple M1 (8 cores, 16 GiB),
macOS 26.4.1 host, colima Linux VM (Ubuntu 24.04, kernel 6.8.0-117, aarch64, 6 cpus, 12.2 GiB). The probe
ran in a `debian:bookworm-slim` container limited to 4 cpus and 8 GB, built with Rust 1.89
(`rust:1.89-bookworm`, `--release --locked`). Load average at start 0.04. No webview was involved.
The binary's sha256 is in the log. Each figure is the median of 5 rounds; I ran the probe 3 times
in one turn and the runs agreed within about 3% (the third large batch run sat highest).

| What | medium (10,000 events) | large (100,000 events) |
|---|---|---|
| `aibus_trace::project` over the events in memory | 2.9 ms | 38 ms |
| Bridge `Projection` request (read file, project, build DTO) | 59 ms | 679 to 693 ms |
| That reply as JSON | 1.76 MB | 17.6 MB |
| Bridge `Events` batch of 500 (start, middle and end alike) | 53 to 54 ms | 610 to 627 ms |
| One 500-event batch reply as JSON | 185 kB | 181 to 187 kB |
| Whole cursor walk, 20 batches | 1.07 s | not measured (200 batches; 200 times 0.6 s is about 2 minutes by arithmetic) |
| Peak resident set of the probe process | 52 MB | 489 MB |

What this says:

- **Each `Events` call re-reads and re-parses the whole trace**, so a batch costs the same wherever the
  cursor is, and a full walk is quadratic in run length. That is the dominant cost I found, and it is
  a Rust-side fix (cache or index the run) that does not depend on the shell choice.
- **`Projection` ships every tool node.** 17.6 MB in one reply at large is not something to push through
  IPC on every update. Condition 6 and the delta rule in condition 4 cover it.
- The projection itself is cheap (38 ms at 100,000 events). Peak memory at large is 489 MB for the
  probe alone, before any webview.

## What the earlier spike measured

The Linux numbers in [B1.1-go-no-go.md](B1.1-go-no-go.md) (window mapped in 312 to 329 ms, about 255 MB

## Unverified (never measured, nothing invented)

- First render, UI latency, webview memory and graph interaction responsiveness at medium and large.
  There is no webview in Mercury's Linux VM and nobody has run WKWebView; jsdom timings would be
  meaningless. A real-webview probe needs the bridge wired in and a graph that can show 500 agents
  (conditions 4 and 5), so it is Phase 2's first measurement, not a gap I could close with a script.
- macOS: build, run, WKWebView version, dockview behaviour, dark mode. Owner steps in VERIFY-MACOS.md.
- React Flow: the spike's graph is a hand-written SVG with fixed pixel size, no virtualisation and no
  memoisation work, so the issue's "test React Flow with memoisation and a bounded visible graph" is
  not done. It moves to #310 (condition 5).
- GPU rendering on Linux (the spike ran with software rendering) and mixed-DPI layout.
- Real traces beyond the one fixture shape; the large dataset is generated.
- The Linux Xvfb build and the host crate's tests were not rerun for this PR.

## What I won't claim

No latency, first-render or webview memory figure at medium or large. No macOS parity. The Linux numbers
are not benchmarks. The Mercury numbers cover the Rust bridge in a Linux VM on an M1, nothing more, and
they are a baseline to compare against, not a target or a guarantee.

## Risks

1. macOS has never run. Mitigation: condition 1, then again at each Phase 2 merge that touches `src-tauri`.
2. The graph and timeline at scale are unverified in any webview. Mitigation: conditions 5, 6 and 10.
3. Bridge I/O is linear in the file per call. Mitigation: condition 4.
4. The IPC surface grows with live runs and controls. Mitigation: condition 7.
5. No real-webview tests, only jsdom. Mitigation: condition 8.
