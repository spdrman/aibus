# 16. Extensions: the SDK, the sandbox host and the registry (EPIC A, #286)

This is what #286 built for spec A2.1 (`epic_a_aibus_workflow_engineering_v3.md`, sections 3, 6.1 to 6.3 and 10.2) on top of the supervisor and the trace (`14-evidence-trace.md`). It covers what an extension is, the manifest and its schema, how the host negotiates with the real CLI, what the sandbox lets an extension do, the registry and the installed store, the `aibus extensions` commands and how to write one. The decisions behind it are D-286 in `docs/DECISIONS.md`; the threats and their tests are in `docs/SECURITY.md`. The Phase 1 gate it starts from is `docs/spikes/A1.5-reference-pilot/`.

## What an extension is

A directory. `aibus-extension.toml`, a licence, a readme, `fixtures/*.jsonl` with a `*.expected.json` beside each, and nothing that runs. aibus never loads native code or a script from a package (no native plugin, unstable Rust ABI; no script). The one kind of code a package may carry is a WASM guest ("WASM guests" below): it has no authority at all, it exists only in a build with the `wasm` feature, and it is hashed and signed like every other file. The host alone starts a process, and only a program on the host's own allowlist of official CLIs (see "Which programs run"), through the supervisor (`14-evidence-trace.md`). A manifest *names* a program; it never decides that the program counts as an official CLI.

That is enough for the two things an extension has to say. How to launch the CLI (a static argv, an environment allowlist, a limit request, optional flags the probe has to find) is data. How to read its events is an engine, and there are three:

| Engine | For | State | Who owns the code |
|---|---|---|---|
| `builtin:claude-stream-json` | The Claude Code stream | Stateful: tool use to agent maps, dedupe across the stream and hook channels, a `finish` step at process exit | The host (`aibus_supervisor::Normalizer`) |
| `declarative-jsonl` | A CLI whose events are one JSON line, one event | None beyond counters and the tool uses still open | The host (`aibus_extension::declarative`), driven by the manifest's rules |
| `wasm-module` | A CLI whose events need state the rules cannot express | Whatever the guest keeps, inside its own memory | The third party (a WASM module in the package), run by the host (`aibus_extension::wasm`) behind the `wasm` cargo feature |

Both are `aibus_supervisor::Engine`: `start`, `stream_line`, `hook_line`, `stderr_line`, `gap`, `finish`, per attempt. This is amendment E1 of the Phase 1 gate: a declarative-only manifest cannot express Claude's normaliser, so the normaliser is a per-attempt stateful object and `supervise` runs whichever one the manifest names. A CLI whose events need state across lines and is not Claude's is the `wasm-module` engine: a guest with the same shape, run in a sandbox that gives it no authority (#333, "WASM guests" below). A manifest that names `wasi-component` is refused like any other unknown value, and so is one that names `wasm-module` in a build without the `wasm` feature.

## The manifest (schema versions 1 and 2)

Strict: an unknown key, a wrong type or a value outside these rules is a refusal that names the field (`aibus_extension::manifest::Manifest::parse`, at most 64 KiB). `docs/schemas/extension/manifest-v1.json` (schema 1) and `manifest-v2.json` (schema 2) say the shape in JSON Schema; the rules a schema cannot say are marked below. `examples/extensions/template/aibus-extension.toml` is the annotated starting point.

| Block | What it says | Rules |
|---|---|---|
| `schema_version`, `id`, `version`, `name`, `kind`, `provider`, `license`, `source_url`, `[publisher]` | Identity | `schema_version = "1"` or `"2"` (the next section). `id` is lower-case reverse-DNS with three to eight labels. `version` is exactly `x.y.z`. `kind = "official_cli"`. URLs are `https`, with no credentials. **The id and the name never contain "Claude Code"** (E6) |
| `[compat]` | `protocol`, `os`, `cli_versions` | Ranges are comparators (`>=1.0.0, <2.0.0`). `os` is any of `macos`, `linux`, `windows` |
| `[cli]` | `executable_candidates`, `vendor_urls` | Executables are file names, never paths. Vendor URLs are the provenance |
| `[auth]` | `owner = "vendor_cli"`, `credential_access = "forbidden"`, `login_argv`, `status_argv` | The CLI owns its sign-in; aibus never reads, copies or stores the token |
| `[execution]` | `argv`, `prompt = "stdin"`, `stdout = "jsonl"`, `env_allow`, `[[execution.optional]]` | **The prompt goes on stdin, never in argv** (E2): no placeholder exists. An argv token is a plain word (no space, slash, quote, `$`, backtick, tilde or brace, and nothing that means "run without asking": `dangerously`, `skip-permissions`, `yolo`, `bypass`, `no-sandbox`, `auto-approve`, `allow-all`). `env_allow` names are upper case and never credential-shaped (key, token, secret, password, credential, auth, cookie, session id), never `AIBUS_*`, `LD_*`, `DYLD_*`, `PATH`, `NODE_OPTIONS`, `PYTHONPATH` and the like, never `CLAUDECODE` or `CLAUDE_CODE_*` (E3) |
| `[limits]` | What the extension asks for | Above zero. The host's ceiling wins |
| `[normalizer]` | `engine` and, for `declarative-jsonl`, one to 64 `[[normalizer.rule]]`, or for `wasm-module` a `module` | A built-in engine takes no rules. `module` is only for `wasm-module`, which takes no rules and needs one: a `.wasm` file directly under `wasm/` in the package. A rule is a JSON pointer, a string it equals and an event kind (`message_chunk`, `tool_started`, `tool_completed`, `tool_failed`, `usage_reported`); `id_pointer` only for the tool kinds, token pointers only for usage |
| `[capabilities]` | All thirteen declared | `supported`, `probe_required` or `unsupported`. Spec 3's twelve plus `hook_channel` (E5). **`session_resume` has to be `unsupported` when `native_child_lineage` is not**: native children die with the lead process (C1, E5) |
| `[[probe]]` | For each `probe_required` capability | The `--help` flags it needs and an optional minimum CLI version. A probe for any other capability is refused |
| `[hooks]` | `needs_delivery` | The extension's evidence is better with hook payloads (E4) |
| `[runtime]` | `usage_quality` | `reported`, `estimated` or `unknown` (E5) |
| `[permissions]` | One acceptable value each | `spawn_only_declared_cli = true`, `read_provider_credentials = false`, `external_network_from_parser = false`. Anything else is refused, so a reviewer reads one block |
| `[policy]`, `[fixtures]`, `[notes]` | Owner and review date, the recorded streams, upgrade and rollback notes | Spec 6.2 requires each of them. Fixtures are `fixtures/<name>.jsonl` and have to be in the package |

## Schema 2: typed flags (#334)

Schema 1 has static tokens and value-less optional flags, so a flag that takes a value, `--model` or `--agents`, had no contract. Schema 2 adds one block, `[[execution.typed]]`: a `flag` and a `kind`, nothing else (at most eight; a `value`, a `default`, a `template`, an `argv` or any other key is refused, and so is a kind that is not one of these). The host fills the value from the plan, and it is never an argument string a manifest wrote.

| Kind | What the host puts in the launch | What it checks |
|---|---|---|
| `model_id` | one argument, the model id the plan names | `[A-Za-z0-9][A-Za-z0-9._:/+-]{0,127}`: it cannot start with a dash, hold a space, a quote, a shell character or a second argument |
| `agent_list` | one argument, a JSON object the host builds with `serde_json` from the plan's agents: `{"name": {"description": "...", "prompt": "..."}}` | one to 16 agents, a unique lower-case name of up to 48 characters, a description of up to 200 and a prompt of up to 8000 characters, no other field |
| `workdir_path` | one argument, an absolute path | the plan's path is relative and plain (no `..`, no root), its directory resolves inside the working directory and so does the path itself when it exists, so a link cannot lead out |

Which flags can be typed is the host's list per CLI (`flags::typed`): `--model` as `model_id` for claude, codex, gemini and kimi, `--agents` as `agent_list` for claude, `--output-last-message` as `workdir_path` for codex. A manifest that types any other flag, or a listed flag as another kind, is refused, and so is one for a program the host has no list for. A typed flag is never also a static token (argv, auth argv or optional flag), so a manifest cannot write the value either. The plan reaches the host as `Grant.typed` (flag to `TypedValue`); `sandbox::typed_args` builds the pairs, in the manifest's order, right after the manifest's argv, and a flag the plan has no value for is left out. `check_launch` runs the same check on a finished launch: each typed flag at most once, followed by one value of its kind, and nothing else after the manifest's argv except its optional flags. A schema 1 manifest with a `[[execution.typed]]` block is refused.

**How an older host says no (it fails closed, with its own error).** A schema 2 manifest has to ask for `compat.protocol` 1.1.0 or later (a range that contains 1.0.0 is refused), and this host speaks protocol 1.1.0 (`negotiate::PROTOCOL`). A host from before schema 2 does not read the typed block at all: its strict parser refuses the manifest with an unknown-field error (`unknown field typed`), which still fails closed, and the protocol range is what tells a host that does read the manifest (and any later one) that this extension needs 1.1.0. A host that reads schema 2 reads `schema_version` before any other key, so a manifest of a schema it does not read (a future 3) is refused by name, with the schemas it does read, and not by whichever new key it meets first. Install lists every typed flag with its kind, and a typed flag a new version adds is an escalation the user accepts by name (`typed:--agents`).

## Schema 2: rule conditions (#357)

A declarative rule has one pointer and one string. A CLI that says what a line is in two places (Codex: `type = "item.completed"` and `item.type = "command_execution"`) needs more, so a schema 2 rule may carry `when`, up to three `{pointer, equals}` conditions the same line has to meet. The first rule whose pointer and every condition match wins, so list the narrow rule before the wide one. The event's native type is the line's words in order (`item.completed/command_execution/failed`). A schema 1 manifest with `when` is refused (`normalizer.rule`), and a host from before this key refuses it as an unknown field, which fails closed.

## The event contract

An engine hands the host events in the trace envelope (`aibus-trace`, schema 2; `docs/schemas/extension/event-v1.json`):

- Event ids are uuid v7 and ascend in the order the events were made (D-319); the order of a trace is the id.
- Every event has an evidence level in `visibility` (`observed`, `correlated`, `inferred`, `unavailable`). A derived event is never `observed`; an event from the CLI cites its raw line.
- Every number is a metric with a data quality (`reported`, `derived`, `estimated`, `unknown`). A missing number is `null` with quality `unknown`, never zero.
- A line the engine cannot map is a `trace_warning`, a line that is not an object is a `gap_detected`, and nothing is dropped. A tool use that never reported back ends the attempt with a `tool_outcome_unknown` gap.
- The attempt ends once, last, with `attempt_completed` or `attempt_failed`, when the process ends.

`aibus extensions test` checks each of these on every fixture and names the check (`basic: event ids ascend (uuid v7)`).

## Negotiation and probes

`negotiate::negotiate` takes the manifest and what `--version` and `--help` said. In order: the protocol range has to contain this host's (`1.1.0`), the operating system has to be listed, the CLI's version has to be in `cli_versions`; then each capability gets a verdict. `supported` and `unsupported` stay as declared (an extension cannot gain a capability the CLI happens to have), `probe_required` follows the probe flags and minimum version, and each unsupported verdict carries its reason. For `hook_channel`, when the manifest says `needs_delivery`, the verdict is `unsupported` with the reason that the host has no live way to receive hook payloads yet (E4; the inline `--settings` route is untried). The stream is then the only evidence, and a trace says so.

For the Claude engine the host also runs the supervisor's own probe (`cli::probe`): the required flags, the 2.1.0 floor and the refusal of a CLI whose `--help` says bare mode is the default for `-p`.

## Which programs run

The host keeps a short allowlist of official CLI program names: **claude, codex, gemini, kimi** (`sandbox::OFFICIAL_CLIS`). The user can add their own names in their policy file, `extra_official_clis = ["mycli"]` in `<config>/extension-policy.toml`; a manifest can never add one. This is the owner's default, to be confirmed: I put it in after the review of #332 and recorded it in D-286.

- `prepare` searches only for the manifest's names that are on the list, in the host's own search directories, and resolves the one it finds to an absolute path itself. A manifest whose names are all off the list gets `NotOfficial` and nothing is searched. `check_launch` asks the same of any launch, whoever built it.
- Refused outright, in a manifest and in `extra_official_clis`: shells, interpreters, package managers and fetchers (`sh`, `bash`, `zsh`, `python`, `perl`, `ruby`, `node`, `deno`, `bun`, `npx`, `npm`, `pnpm`, `yarn`, `pip`, `pipx`, `uv`, `gem`, `cargo`, `go`, `brew`, `curl`, `wget`, `env`, `sudo`, `doas`, `su`, `ssh`, `nc`, `socat`, `busybox`, `xargs`, `osascript`, `pwsh` and the rest of the list in `manifest::forbidden_program`, with a trailing version ignored). For a program that is not one of the host's four, argv with the shape of an install or an eval (`install`, `add`, `exec`, `eval`, `-c`, `-e`, `-m`) is refused too; an official CLI's own subcommands are its own (`codex exec --json` is fine). `@` is not a token character.
- **The resolved-name check is best effort.** After the search, if the file an allowlisted name resolves to is itself called a shell, interpreter or package manager (`claude` symlinked to `python3`), it is refused. That is all it does: a link to `nodejs`, `rbash`, `mksh`, `awk`, `bash-5.2`, `mise`, an npm `cli.js` or a wrapper script still launches, because the name says nothing about what the file is. The allowlist is only as trustworthy as the user's own search directories and policy file: a directory or a policy an attacker can write defeats it, and the host does not defend against that.
- A manifest has no setup step. There is no `prepare` table (an unknown key is a refusal), nothing a package says runs to get it ready, and if a later schema adds setup steps they will be declared, shown to the user and run only after a confirmation that names the exact command.
- `aibus extensions install` and `update` print each program, whether it is on the allowlist (an extension for an off-list program installs but will not run until the user adds it) and the whole argv.
- The flags a manifest may pass are an allowlist of flags per CLI (`aibus-extension/src/flags.rs`). The host owns one list for each of claude, codex, gemini and kimi: every flag in `execution.argv`, in the two auth argv and in every optional flag has to be on the list of each official CLI the manifest names, with a value the list allows (`--setting-sources` takes `user` only, `--sandbox` takes `read-only` or `workspace-write`, `--config` takes `model=`, `model_reasoning_effort=` and a few other keys, `--output-format` takes the formats the CLI has). The words that are not flags are on a list too (`claude auth`, `login`, `status`; `codex exec`, `login`, `status`), so `claude mcp add` and `codex apply` are refused, and a short switch takes nothing attached, so `-dy` and `-pc` are not read as two switches. A flag that is not on the list is refused, whatever its spelling: `--setting-sources=project`, `--plugin-dir`, `--mcp-config-file`, `--settings-file`, `-c sandbox_workspace_write.network_access=true` and a custom `--profile` all fail for that reason, and so does every flag nobody has read yet. A manifest that names an official CLI and another name has to pass every official list. A program the user added with `extra_official_clis` has no list, so only the denylist applies to it, and `check_launch` applies the same list again to what is really about to run.
- The lists are maintained per CLI version. Each is written against the flags the CLI documents in the release an extension targets (`compat.cli_versions`); a flag a newer CLI adds stays refused until someone reads what it does and adds it to the list, and a flag that changes meaning is taken off. The lists are in code, not in a manifest or a policy file, so an extension cannot widen its own.
- The "run without asking" denylist (`--full-auto`, `-y`, `--yes`, `--allowedTools=Bash`, `--permission-mode=acceptEdits` and the separate-value form, `--sandbox=danger-full-access`, `--ask-for-approval=never`, `--dangerously-*`, `--config key=value` settings of an approval policy or a sandbox mode, `--settings`, `--mcp-config`, `--add-dir`, `--permission-prompt-tool`, ...) stays as a second check over the same tokens, and it is the only flag check for a name the host has no list for. It is still a list of spellings known today, not a proof, so the argv is printed at install; the boundary is the two allowlists (programs and flags) and what the user accepts.

## The sandbox host

`sandbox::prepare` is the only place a manifest becomes a launch, and `sandbox::check_launch` is the check every launch has to pass whoever built it.

- **Which program.** One of the manifest's file names, found in the host's own search directories by `cli::discover_from`: a relative directory is refused, so is a file others can write, one in a directory others can write, one owned by someone else, and one that does not print a version. The launch carries the declared name, so a swapped target is the supervisor's existing trust boundary, not a new one.
- **Which arguments.** The manifest's static tokens, then the optional flags the caller asked for and the probe found. A flag the caller needs that the CLI lacks is an error, never a silent drop.
- **Which environment.** `cli::bounded_env`: `PATH=/usr/bin:/bin`, the host's allowlist, then the manifest's `env_allow`. No credential-shaped, `AIBUS_*`, loader or session name ever reaches the CLI, whatever the manifest says, and the keychain is never opened here. Files under `HOME` are not protected by this (below).
- **Which directory.** The one the host granted, resolved, absolute and existing. A manifest cannot name a path.
- **Which limits.** The smaller of the request and the host's ceiling, field by field (wall time, stdout, line, stderr, lines a second). The supervisor enforces them: SIGTERM, then SIGKILL to the whole process group.
- **Which network.** None from aibus: no package code runs. The vendor CLI talks to its vendor, as it does outside aibus.

**What this is not.** It is not an operating system sandbox, and it gives the CLI no less than the user has. The host decides which program runs, with which argument, environment, directory and limits, and no package code runs in aibus. Once the CLI is running it is the user's process with the user's rights: it gets `HOME` (its own sign-in lives there, so it has to), so it can read other files under `HOME` and write outside its working directory, and nothing blocks its network. A grandchild that keeps stdout open can make a clean exit read as a wall-time stop. An OS sandbox around the CLI is not here (see "Not here"). A descendant that leaves the process group (`setsid`, `setpgrp`, a double fork) no longer outlives the attempt (#338, #352): kernel-backed on Linux with the helper, best effort on macOS, with the limits in the next paragraph.

**Descendants (#338, #352).** The supervisor starts the CLI as the leader of its own process group, and at the deadline, on cancel and when the attempt ends it sends SIGTERM and then SIGKILL to that group. That reaches everything that stayed in the group. For a descendant that left it (`setsid`, `setpgrp`, a double fork) the guarantee depends on the system. **Linux, with the helper (kernel-backed):** the caller that runs an extension unattended sets `Launch::helper` to the `aibus` binary, and the CLI then runs under a hidden mode of it that is a child subreaper (`PR_SET_CHILD_SUBREAPER`). The kernel hands every process that loses its parent anywhere under the CLI to the helper, a standard daemon double fork (`setsid -f`, `daemon(3)`, the middle process exits at once) included, so the tree is complete at every moment. When the CLI exits, when the deadline or a cancel asks (SIGTERM goes to the CLI's group first, SIGUSR1 ends the whole tree after the grace period, also for a CLI that ignores TERM) and when the supervisor dies (parent-death signal, plus a parent check on every turn), the helper stops what it finds under itself, looks again until nothing new turns up, kills it, reaps it and exits with the CLI's own status (an exit code, or the same signal). What is still not guaranteed there: a process in the middle of an escape is only caught by the kernel's reparenting, which holds, but things started through a broker are not descendants at all (`docker run -d`, `systemd-run`, `launchctl` or `open`, `at`, a session in an already running tmux or screen server), a shared server the CLI itself started is killed with its tree, and the helper finds the tree with `ps`, so on a host without a usable `ps` it can reap and forward signals but not enumerate, and warns once (a cgroup would not need `ps`, and is not here). **macOS, and Linux without the helper (best effort):** macOS has no subreaper, so only the user-space sweep of #338 holds: a sampler reads the process table (`ps`) every 50 ms (about 70 ms with the time `ps` takes) and remembers each process that descends from the CLI by pid and start time; at the end every remembered process that is still the same one, and everything under it, is stopped (SIGSTOP), looked for again until nothing new turns up, and killed. A `setsid` or `setpgrp` child, or a double-forked child whose middle process lived long enough to be sampled, is ended, including when the CLI exits by itself and leaves it behind. A standard daemon double fork with no linger is usually not caught there, and a process that is trying to escape is not stopped; `tests/descendants_338.rs` runs the no-linger case on Linux and keeps it ignored elsewhere. The sweep also runs on Linux next to the helper, as a second net. A host with no `ps`, or a busybox `ps` without `-ax` and `-o lstart`, tracks nothing: one warning goes to stderr and only the group kill holds. The sweep runs `ps` on the calling thread, so on a current-thread runtime it holds everything else for tens of milliseconds, a few times over. The helper mode is internal: it is picked before the command line is parsed (so it is no subcommand, no completion and no help line, and no flag of any CLI reaches it), it refuses to run with a terminal on stdin, it runs only an absolute path, it adds nothing to the environment and opens no file, and `check_launch` accepts no helper but the running `aibus` binary. #288 on Linux uses it.

## The registry and the installed store

A registry is a directory with `aibus-registry.json` (`registry-v1.json`): entries `{id, version, hash, path, signature?}` and a revocation list `{id, version?, hash?, reason}`. No network service, nothing fetched. The hash is `sha256-tree-v1:` over the sorted lines `<path> NUL <sha256 of the file> LF`, so one changed byte, one added file or one rename changes it. The index is at most 1 MiB and 4096 entries, with no duplicate (id, version) and no path that climbs.

Every fetch re-reads the package (`package::read`, walking by descriptor with `O_NOFOLLOW` at every step: no symbolic link and no hard link anywhere, empty directories counted, no special file, at most 256 files, 4 MiB a file, 16 MiB in all, six directories deep, plain ASCII names, no two names that differ only by case) and checks, in order: the manifest names the entry's id and version, the hash is the entry's, the registry's and the user's revocations, the signature, the publisher allowlist, and compatibility. A failure is filed as `revoked`, `provenance_invalid`, `incompatible` or `malformed`, and `install` records it as a quarantine and activates nothing.

The user's policy is `<config>/extension-policy.toml` (`require_signature`, `extra_official_clis`, `[trusted_keys.<name>]` tables (an ed25519 public key `key` in hex, `ids` and `prefixes` it may sign, an optional `revoked` reason; an old file with a bare hex string per key is refused and the error shows the table to write), `allow_publishers`, `[[revoke]]`). With no file, nothing is required; a file another user can write, or that is owned by someone else, is refused. A signature covers `aibus-extension-v1`, the id, the version and the hash, and a key may only sign the ids in its scope: an exact id, or a prefix that matches at a label boundary (`org.devshell.aibus` covers `org.devshell.aibus.x`, not `org.devshell.aibusx.x`). Only this file sets a scope; a registry entry or a package that carries one is refused. A revoked key quarantines the versions it signed and nothing else (D-335). Signing a package is the publisher's own step (`ring`, `ssh-keygen` or anything that makes ed25519); `aibus extensions publish` records a hash and leaves the signature field to the publisher.

The store is `<data>/extensions/` (`state.json` under a lock, and `packages/<id>/<version>/`, all `0700` and `0600`). It keeps every installed version, the active one, the previous one for `rollback`, a pin and a disabled flag per id. Resolving an extension for use re-hashes it every time, so a file changed after the install quarantines it (`tampered`) instead of running.

Revocations are checked at install, update, rollback, resolve and verify. The store keeps the revocations of the last registry any command read, so `resolve` and `rollback` need no registry; `rollback` refuses a revoked version and `resolve` does not serve one (it quarantines it); `verify` fails, and says why, when the registry cannot be read, instead of printing `ok`. A pin holds against `install` as much as `update`. A version number names one content: a registry that offers an installed (id, version) with other bytes is refused as `provenance_invalid`, and the installed copy stays. The store keeps the manifest of the last version the user accepted and compares with it, so an unreadable or quarantined active copy neither skips nor empties the escalation check (an unreadable active copy fails the install as `tampered`).

An update never goes down: a version below the active one is a downgrade, refused, and a registry that replays an older index changes nothing. An update that asks for more than the installed version (a new executable, environment name, optional flag, argv token, capability, engine, a larger limit, hook delivery) is a capability escalation: it is refused with each item named (`executable:othercli`, `env:EXAMPLE_HOME`, `capability:workspace_control`, ...), and nothing changes until the user repeats the command with `--accept <item>` for every one.

## Commands

```
aibus extensions [--registry DIR] search <query>
aibus extensions install <id>[@<version>] [--accept <item>]...
aibus extensions verify <id>
aibus extensions list
aibus extensions update <id> [--accept <item>]...
aibus extensions disable <id> | enable <id> | pin <id> | unpin <id> | rollback <id> | remove <id>
aibus extensions test <path-or-id> --fixtures
aibus extensions publish <dir>
```

The registry is `--registry`, else `$AIBUS_EXTENSION_REGISTRY`, else `<config>/extension-registry`. Spec 6.2 writes `<publisher/name>@<version>`; the id is a reverse-DNS name, so it is `<id>@<version>` here. Exit codes: 2 for a name that does not exist, a bad version or a registry that cannot be read; 6 for a refusal the user has to act on (a quarantine, an escalation, a pin, a downgrade, a disabled or quarantined extension); 1 when a conformance check fails. `--json` prints one object for `list` and `test`.

## Writing one

1. Copy `examples/extensions/template/`. Change the id (a domain you own), the executable name, the argv, the rules and the fixtures.
2. Record a real stream of your CLI into `fixtures/<name>.jsonl`, then write `fixtures/<name>.expected.json` (`fixture-expected-v1.json`): the ending, the attempt status and the event kinds in order. `AIBUS_BLESS=1 cargo test -p aibus-extension --test reference bless` writes them from what the engine makes now, for you to read before you keep them.
3. `aibus extensions test ./my-extension --fixtures` runs them offline.
4. `aibus extensions publish ./my-extension --registry ./my-registry`, share the directory, and anyone can `aibus extensions install <id> --registry ./my-registry`.

Nothing in the core source changes for any of it; `crates/aibus/tests/extensions_cli.rs::a_third_party_extension_round_trips_without_a_core_change` is that, end to end.

## The reference extension

## Runtimes and the OpenRouter rule (#359)

A workflow step names a runtime: `aibus`, `cli.claude`, `attached`, and since A2.2 `cli.codex`, `cli.gemini` and `openrouter`. Jev (`workflow/jev.rs`) holds what each offers. `cli.codex` and `cli.gemini` carry what their extensions declare supported (Gemini has no `login_status` and no `structured_events`, which its manifest leaves to a probe); Codex is `experimental` and Gemini `unverified` (never run), and both plan without running until the scheduler (#288). `openrouter` is the one direct API runtime: `cancel`, `headless`, `one_shot` and `usage_report`, and nothing a vendor CLI gives (no login status, no native children, no resume). **It is never picked unless the user approved it for the run** (`Request.approved`; an `aibus` step whose account is OpenRouter's counts too, once the scheduler passes `Request.account_provider`): an unapproved candidate is skipped, a lone one ends in `openrouter_needs_approval`, and the decision's evidence carries the proposal, one line each for billing (separate OpenRouter credits, not a subscription allowance), models (downstream, per request), data (the prompt goes to OpenRouter and the model provider) and capabilities. A CLI that lacks a capability is not replaced by OpenRouter either: the step stops for a person. The plan shows an `openrouter` step as `openrouter_run` with its billing and "the openrouter account's own key only". The decision is D-359.

## The consented handoff (#360)

A step that reads the output of a step that could be another receiver is a handoff (spec 10.2). The boundary is who receives and bills the data, **provider and account**, not the runtime: two `aibus` steps on an Anthropic and an OpenRouter account are a cross-provider move, and the Claude CLI to an `aibus` step on the same Anthropic account is not. The plan lists what it can see under `handoffs` (`from`, `to`, `via`, both runtimes, `needs_consent`, `accounts: "resolved when the step runs"`; absent for a chain that stays on one runtime). It knows the provider a runtime implies and not the account, so two `aibus` steps on different accounts are not in it; the run checks again with the real ones.

`workflow/handoff.rs` is what a scheduler uses at run time. `needs_consent` compares provider and account, always asks when either is empty or a placeholder, and takes the provider of a vendor CLI or OpenRouter step from its runtime. `preview` says run, plan, from whom to whom, who receives and bills, and each item by name, size and hash, never its content. `record` builds the artifact (`aibus.workflow.handoff`): a canonical lower-case uuid v7 id, the state (`granted`, `declined` or `not_needed`, an enum, never a free string), who and when, the transfer with its run id and plan hash, and the hash of the preview; it refuses an id that is not a uuid v7 of the RFC 4122 variant, an empty name, and a hash that is not the preview of this transfer. It builds the value; the scheduler stores it. `deliver` is the only way out: it refuses unless the state is `granted`, or `not_needed` when the recorded parties really share provider and account (re-derived, so a relabelled `declined` refuses); the recorded preview hash matches the recorded transfer; the run, plan, source and destination now are the recorded ones (a consent for Codex to Claude does not deliver to OpenRouter, or in another run); the consent is unused (spent by its preview hash, so a copy under a new id is the same consent, and the scheduler must persist the spent set); and the bytes, hashed inside the call, equal the shown items as a multiset. It returns the bytes it hashed, so there is no second read, and marks the consent spent only on success.

**What it does not cover.** Data that moves through a shared working directory (the live pair itself passes the text through `--output-last-message` in the first step's directory, and a second CLI in the same directory can read anything the first wrote); a `{{prev...}}` read when a step has more than one incoming route (`Workflow::source` finds no single source, so there is no edge and no handoff); and the accounts of two `aibus` steps at plan time. `examples/workflows/cross-provider.toml` is Codex then Claude Code. `fixtures/workflows/handoff-live-2026-11-15.json` is one live pair through `deliver`: Codex (0.167.0) wrote one sentence to a file, the preview was recorded and granted, and Claude Code (the reference extension) got the bytes `deliver` returned; hashes and sizes only. **The consent in that run is a test operator's environment variable, not a person answering a prompt**, and nothing in the TUI or the CLI asks for it yet: asking is the scheduler's job (#288). The decision is D-360.

## WASM guests (#333)

A third party's stateful parser is a WebAssembly module, named by `normalizer.module` and carried in the package (`wasm/<name>.wasm`, at most 4 MiB like any file). It is part of the content hash, so the registry's hash check, the installed store's re-hash on every resolve and the ed25519 signature all cover it, and a different module under the same version is `provenance_invalid`. A new module path in an update is an escalation (`module:<path>`), and so is moving from rules to a module (`engine:wasm-module`). The runtime is wasmtime (Apache-2.0 with the LLVM exception, which `deny.toml` now lists), pinned to the 36.0.x long-term-support line: the newest release that builds on the workspace's Rust 1.89 (40.0.4) has open security advisories, and 36.0.20 has none. Which runtime to host was my choice, made without the owner's review; it is reversible, because it sits behind one feature and one module.

**No ambient authority.** The module is built for `wasm32-unknown-unknown`, not WASI. The host links three functions, module `aibus`, and refuses at load (`package::read`, `Module::load`) a module that imports anything else, with another signature, or as another kind of import (a memory, a table, a global):

| Import | Signature | Does |
|---|---|---|
| `read_line` | `(ptr i32, cap i32) -> i32` | Copies the current stdout line to `ptr`. Returns its length, or `-1` when `cap` is too small (nothing is copied). Stderr and hook lines never reach a guest |
| `emit` | `(ptr i32, len i32) -> i32` | Hands the host one normalised event, as a JSON object. `0` taken, `1` refused |
| `next_seq` | `() -> i64` | The host's next sequence number: monotonic per attempt, from 1. The guest cannot set it |

The module exports `memory` (32-bit, not shared, at most 16 MiB at the start), `on_line() -> i32` (once per stdout line) and `on_finish() -> i32` (once, after the last line). A return value other than `0` is a failure. A start function runs under the same limits. No threads (wasmtime is built without them), no relaxed SIMD, canonical NaNs, so the same input gives the same events.

**What the guest chooses, and what the host does with it.** A guest event is `{kind, native_type?, tool_use_id?, data?, origin?, visibility?}`. The kind is one of `message_chunk`, `tool_started`, `tool_completed`, `tool_failed`, `usage_reported`, `trace_warning`, `gap_detected`: never an `attempt_*` event, which only the host writes. Everything else on the event is the host's: the event id (uuid v7, from the host's own generator, so ids ascend and a guest that writes `event_id` or `attempt_id` is ignored), the attempt, the timestamp, the parser name (`wasm-module/1`), the raw-line hash and the `raw:stdout:L<n>` citation. The origin and evidence level are clamped: from a line, `cli_stream` and `observed` at best; a guest that says `derived` gets `derived`, at best `inferred`; at the end of the stream there is no line to cite, so an event is `derived` and at best `inferred`, with no hash. A guest can ask for a weaker level, never a stronger one, and it cannot say `aibus_scheduler` or `hook`. `usage_reported` metrics are held to the manifest's `runtime.usage_quality` (`estimated` downgrades `reported`; `unknown` drops the number) and to whole numbers up to 2^53, as the declarative engine does. An event that is not JSON, is not an object, has a kind outside the list or a field of the wrong type is refused with a `trace_warning` (`guest_event_refused`, and the reason), and is never stored.

**Limits.** Per call: 10 million units of fuel and a 500 ms wall deadline (wasmtime epoch interruption, ticked every 10 ms by one thread per compiled module). Per instance: 16 MiB of memory, one memory, one table of at most 10,000 elements. Per event: 16 KiB. Per call: 64 events. Per attempt: 4 MiB of events and 16 refused events. These are the host's ceiling (`wasm::Limits::default`): a manifest cannot ask for more. A guest that spins, traps, runs out of stack, returns non-zero, hands over a pointer outside its memory, or writes past a cap is stopped: one `gap_detected` says `extension_failed:<fuel|deadline|trap|bad_return|bad_pointer|output_limit>`, the guest is never called again, the lines after it are counted and not read, and the host still writes the attempt's terminal event. The events it handed over before it failed are kept (the host checked each one).

**What it does not do.** It is not a defence against a guest that is merely wrong: a guest can describe a stream falsely within its clamps (a `tool_completed` for a tool that failed), and the evidence trail is its raw-line hash, so the conformance fixtures and the user's reading of the first run are the check. A guest that busy-loops costs up to the deadline per line. Wasmtime is a large dependency with its own security advisories; the pin is reviewed, and `cargo deny check advisories` runs on it like the rest of the tree.

**Writing one.** Compile any language to `wasm32-unknown-unknown` with the three imports above. `crates/aibus-extension/tests/wasm-guest/` is a guest in Rust that does what the template's rules do and keeps the tool uses still open, so at the end of the stream it reports their outcome as unknown (a stateful thing a declarative manifest cannot say). Its source, `Cargo.lock` and `build.sh` are checked in, and so is the built `parser.wasm` with its sha256, so the tests need no wasm target; `build.sh` builds it in a container (always the x86_64 image: the compiler's output differs by architecture) and the result is the same on every docker host. `aibus extensions test <dir>` runs the conformance runner over a guest like any other extension, and a test shows the guest's events equal the declarative engine's for the reference streams.

**What it costs.** Measured on the MacBook (aarch64, release profile, a clean target directory each time): `cargo build --release -p aibus-extension` takes 35 s wall and 215 s of CPU without the feature, and 49 s wall and 384 s of CPU with it, about 170 s of CPU more, from some 200 extra crates (wasmtime and cranelift). The whole `aibus` release binary goes from 31.4 MB to 40.2 MB, 8.9 MB (28%) more, the compiler in it. That is why the feature is off by default, in the release build too, until the owner decides. The checked-in guest is 79 KB.

## Not here

- **An operating system sandbox, and a way to keep files under `HOME` away from the CLI.** The CLI needs `HOME` for its own sign-in, so the answer is a sandbox profile per CLI (macOS `sandbox-exec`, Linux landlock or a container), and it is a design of its own.
- **WASI, and a WASM host in the release binary.** A guest may not import a single WASI function (no clock, file, socket, environment or random: the host API below is all it gets), so a module built for `wasm32-wasip1` is refused at load. The host is behind the `wasm` cargo feature, which is off by default: wasmtime is most of the extra build time and binary size (see "What it costs"), and whether a release build carries it is the owner's call.
- **A guest for the built-in Claude engine, hook delivery to a guest and a guest that spawns anything.** A guest reads the one stdout line it is given and says what it saw. Nothing else reaches it.
- **Typed flags beyond the first set.** Schema 2 types `--model`, `--agents` and Codex's `--output-last-message` (#334); `--max-budget-usd` and the flags of other CLIs are added to `flags::typed` one at a time, each with a kind and a test. Nothing builds the values yet: the workflow compiler (#283) and the scheduler (#288) put them in `Grant.typed`.
- **A package archive.** A package is a directory. A single-file form can reuse the hardened tar reader of `.aibus` bundles (#271) later.
- **Signing from the command line, and a hosted catalog.** The signature is verified and enforced by policy; making one is the publisher's tool. Who signs a curated catalog and where it lives is still open, an owner decision pending (D-335 gives its key a prefix to be bound to, and no more).
- **Live hook delivery** (E4), **an operating system sandbox around the CLI**, and **a live run of the reference extension from the command line** (the scheduler, #288, launches runs).
