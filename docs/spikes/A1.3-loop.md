# A1.3 spike: core types, graph layout, side store and the Elm loop

D-03 and D-04 say the loop can commit once per message and that heavy values can live outside the graph without hurting. I built both on the mini engine and measured the commit that matters most, a streamed chunk.

## The measurement

Fixture (`crates/aibus-core/benches/commit_stream.rs`): 8 runs, one of them with a 100,000-line transcript (about 8.5 MiB of text, 99,630 sealed rows plus a 615-row tail at width 100) open in a transcript derived, 2,000 rows in the session log ring, a card derived per run and a status bar derived. The timed call is `App::step(Msg::Stream { .. })`, so it covers `reduce`, the one commit with recompute, and `Effects::after_commit`. 5,000 samples each, release build, 200 byte text chunk plus a usage chunk per message, on MARS (i7-14700F) inside a container with the pinned 1.85 toolchain.

| Case | p50 | p99 | max |
|---|---|---|---|
| Messages round-robin over the 8 runs (the open transcript recomputes on every eighth) | 4 to 9 us | 26 to 53 us | 125 to 270 us |
| Every message to the run whose transcript is open (worst case, recompute each time) | 21 to 37 us | 36 to 53 us | 130 to 230 us |

The budget is 4 ms p99 (03 section 11), so this is about 100 times under it. Three runs of the bench gave 26, 36 and 53 us for the mixed p99 (the host was shared), which is noise at this scale. I did not measure on a 2020 laptop, so the real margin is somewhere under 100x, but a 10x slower machine would still pass.

Why it is cheap: the stream commit writes the tail handle and the usage map, the engine recomputes the open transcript, one card and nothing else, and the transcript derived only counts rows of the tail (the sealed blocks are a cache hit). `bench` also prints the snapshot size (9,810 bytes with 8.9 MiB of content in the store).

I did not run the bench in a debug build, and I only ran it against the mini engine. The causl-rs host layer does not exist yet.

### Where the spec's shape would have failed

03 section 5 makes `model:run:<id>:tail` a `Str` of up to 64 KiB. The commit itself is fine (a 48 KiB `Str` write costs p50 13 us, p99 18 to 35 us), but the engine retains the written value for 4,096 commits, so a single streaming run would pin about 4096 x 48 KiB = 192 MiB of tails, against the 4 MiB the retention section promises. So I made the tail a `Handle { store: "tail", id, version }` whose version moves on every append, and the text lives in the store. That is the only place I diverged from the node types in 03 for a measured reason.

## Deviations from 02 and 03

Things I changed or added, with the reason.

- **`model:run:<id>:tail` is a handle**, see above.
- **`reduce(graph, store, msg, env) -> Vec<(NodeKey, Value)>`**, not `reduce(graph, msg) -> Vec<Write>`. The writes are keyed by `NodeKey` because a message that creates a run writes nodes that do not exist yet; `step` registers them (registration sits outside graph time) right before the commit. `Env { now_ms, ticks_dropped }` carries the two things `reduce` may not fetch itself, so it stays deterministic for replay. `reduce` still mutates the in-memory store (sealing a block, pushing a log row), because 03 section 8 has it bump handle versions.
- **Run ids come from the clock and a counter** (`Ulid::from_parts(now_ms, session bits + eng:run_seq)`) so `reduce` can create a queued run without randomness.
- **`Msg::Persisted` is new.** Something has to reset `model:persist:due` and only a commit can. It writes `eng:snapshot_seq` and `eng:snapshot_ms`.
- **`Command::Delegate` and `Command::Fork` gain `parent: Option<RunId>`.** The `delegate` tool needs to say who asked, or depth and "parent alive" cannot be derived.
- **The store is a cheap-clone handle** (`Store(Arc<Mutex<..>>)`) that deriveds capture, instead of `Tracker::store()`. The `Tracker` lives in `aibus-graph`, which knows nothing about the store. The derived still reads the handle through the tracker so the version is the dependency. Blocks are `Arc<Block>` and never mutate once sealed; the wrapped-line cache lives in the store, keyed by block id, and a width change drops it all (no 2 s grace yet).
- **`view:dirty` is not a commit-metadata derived in core.** The core cannot map nodes to widgets, so `App.dirty` collects `commit.changed_nodes` and `aibus-tui` derives `view:dirty` from them.
- **`view:animating` is registered by core**, as a derived over run statuses (Starting, Running, Compacting). The tick timer needs it, and a key can only be registered once, so the TUI adds its own animation flag as a separate node rather than replacing this one.
- **`step` does not call `persist.after_commit`.** The commit log append and the snapshot write are IO and belong to the persistence issue. The core exposes them as `Effect::Persist` driven by `model:persist:due`.
- **`Effects` hands effects to a sink closure** instead of owning a runtime, provider registry, tool executor and hook runner. Those arrive with A2 and capture what they need. The idempotence rule is the one in 02: effects are keyed (`run:<id>`, `tool:<call>`, `hook:<id>`, `router:<fork>`, `advise:<checkpoint>`, `persist`, `cancel:<run>`), a key is started once, and it is forgotten when it leaves the listing, so a retry starts again.
- **Own `KeyEvent` and `MouseEvent` types**, because the engine must build without crossterm.
- **`persist:due` needs at least one message since the last snapshot** for the 30 s rule, otherwise an idle session would be "due" forever. The first message starts the 30 s clock.
- **Extra keys** beyond the abbreviated list in 03 section 5: `model:hooks:due`, `model:router:queue` (from the table in section 7), `model:last_msg`, and the `eng:` counters (`msg_seq`, `run_seq`, `snapshot_seq`, `snapshot_ms`, `clock_ms`, `shutdown`). `eng:msg_seq` also guarantees every message changes the graph, which is what makes "one commit per message" true even for two identical key presses.
- **`RunStatus::WaitingPermission(id)` is stored as `waiting_permission:<id>`** in the status node.
- **Stream chunks:** usage chunks are added (the fake provider emits deltas), `UsageUpdate` replaces. Thinking and tool-input fragments are not written to the transcript tail.
- **Messages with IO-shaped consequences only log** for now: `SendMessage`, `Workflow`, `CreateHandoff`, and `SubmitPrompt` when a lead already exists. There is no mailbox effect node in the seven yet. `hooks:due` and `router:queue` are drained by `HookFired` and `RouterAnswered` but nothing fills them until A2.
- **`AccountsReloaded` refuses a `key_ref` that is not `keyring:`, `env:` or `file:`** and fails the step with exit code 4 without echoing the value, so a raw key pasted into the wrong field never reaches the graph.
- **`CredentialError`** did not exist in `aibus-provider`, so it is defined in core next to `AibusError`.
- **`transcript_rows`** (a derived over the store's wrap cache) is in core as the shape `aibus-tui` will copy for `view:transcript:<run>:lines`. It wraps by character count; the TUI will swap in unicode width.

## What I noticed

- 03 section 8 says a token arrival re-wraps "a few hundred bytes". The tail can be up to 64 KiB, so a token re-walks up to 64 KiB. I count rows without allocating, which is the 21 us above. Wrapping into owned strings would be several times that, still far under budget, but worth keeping in mind when the TUI wraps for drawing.
- `Effects::after_commit` scans every run for `cancel_requested`, so it is O(runs) per commit (500 runs max). It is invisible at 8 runs. If it ever shows up, a derived list of cancelled runs removes the scan.
- The mini engine's equality cutoff meant I could not rely on a commit that "writes the same thing" to produce a time, hence `eng:msg_seq`.
