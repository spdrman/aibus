# A1.5 spike: can `causl-engine-core` be the second backend?

Short answer: yes. I wrote the host layer, it passes the whole A1.2 conformance suite, a recorded session replays to a byte-identical snapshot on both engines, and the stream commit costs about 1.5 to 3 times what `mini` costs, still around 50 times under the 4 ms budget. The catch is where the crate comes from: it is only reachable with a token, so only the `causl-spike` workflow (or Rom's machine) can build any of this.

## How I got the crate

- **Source:** `https://git.opsite.ca/causl/causl-core-rs.git`, crate `causl-engine-core` under `tools/engine-rs-core`. It is private and needs a token. The public mirror `sheetbaseproject/causl-engine-core` still holds only a README and a licence, so it is not an option yet.
- **Pin:** `a6247b36b38dda4d97017d0577210aa8c724e4f2`, the tip of `chore/512-merge-back`, which is the commit spec 03 section 2 was read against. It is in `crates/aibus-graph-causl/Cargo.toml` as `rev` and in that crate's `Cargo.lock` as the resolved source. Licence is MIT.
- **Access:** Rom added the repository secret `CAUSL_CI_BUILD_1`. Only a workflow can read it. `.github/workflows/causl-spike.yml` has exactly one step that sees it. That step probes the remote with the token (HTTP status only, never the value), then runs `cargo fetch --locked` with the header passed through `GIT_CONFIG_*` environment variables, so nothing is written to a config file. Every later step builds `--offline` from the cargo cache. Gitea answered 200 to both `Authorization: Basic` (user `x-access-token`, the token as password) and `Authorization: token`, and 401 without a header; the workflow uses basic.
- **Reproducibility:** the fetch is only reproducible with the secret. Nobody else can build `--features causl-rs`. The results below come from two runs of that workflow, plus my own runs against a local checkout on MARS (a path override that I did not commit and that never touched an image). The local checkout is a different branch than the pin, so the hosted run is the one that counts for the pinned commit, and both agree.
- **MSRV:** `causl-engine-core` builds and passes on Rust 1.85, so the repo MSRV does not move. Clippy runs on 1.99.1.

## How default builds stay independent of it

Cargo resolves optional git sources into `Cargo.lock` and fetches them to check the graph, even when the feature is off. A `causl-rs` feature on `aibus-graph` would have put a private remote into the root lockfile and broken `cargo build --workspace --locked` for anyone without a token. So the backend lives in its own crate, `crates/aibus-graph-causl`:

- it is listed under `exclude` in the root `Cargo.toml`, so it is not a workspace member and has its own `Cargo.lock` (seeded from the root one, so the pinned versions of smol_str, proptest and friends are the same);
- the `causl-rs` feature and the git dependency are optional and live only there; with the feature off the crate is empty;
- the root `Cargo.lock` and root `deny.toml` never mention the remote (`allow-git = []` stays). The crate has its own `deny.toml` whose `allow-git` lists exactly `https://git.opsite.ca/causl/causl-core-rs.git`.

I ran the root gates in a container that had no copy of the private source and no credentials, and `cargo build --workspace --locked`, `cargo test --workspace --locked`, clippy and `cargo deny check` pass (details in the PR). Building the excluded crate itself without the token fails on the fetch, which is the expected cost of the split.

One deviation from the spec text: the type is `aibus_graph_causl::CauslGraph`, not `aibus_graph::causl::CauslGraph`. It has to be a separate crate for the lockfile reason above, and `aibus-graph` cannot depend on it. To make that possible I made the fields of `Node` and `Unsubscribe` and `Tracker::new`/`Tracked` public in `aibus-graph`; nothing else in `aibus-graph` changed.

## The host layer

Around 700 lines in `crates/aibus-graph-causl/src/lib.rs`:

- Keys map to engine ids with one slot per node (slot = node index). The engine keeps inputs and deriveds in two tables that both start at slot 0, so a node id can name two cells; I use one shared counter and retire the placeholder cells the engine auto-creates for the other kind.
- A `ComputeCallback` runs the registered closure through the aibus `Tracker` and returns the recorded reads as the new dependency list. Values the closures see are the typed aibus `Value`s, not the engine's JSON.
- Values cross as tagged JSON (`{"$t": "f64" | "i64" | "bytes" | "handle" | "map", "v": ...}`) because the engine only has `Number(f64)`: plain numbers are always `I64`, and `F64`, big ints, bytes and handles are tagged so nothing is lossy and the engine's equality cutoff still tells `I64(1)` from `F64(1.0)`.
- A `SubscriberCallback` collects the engine's firing batch; the host dispatches it after the transition, because aibus observers also get the finished `Commit`. The order is the engine's (insertion order per node, then changed order).
- Commit log, versions, `explain` and the typed current values are host state. `read_at`, retention, dependencies, dependents, atomic rollback, equality cutoff, time and commit-metadata recompute all come from the engine.
- `snapshot` is the typed input map, `hydrate` is one forced commit of all inputs with `originated_at` set, `simulate` runs the same transition on a clone of the `State`.

## Conformance result (A1.2 suite, `--features causl-rs`)

All 13 cases pass, on MARS and on the hosted runner against the pinned commit, plus the differential test (the recorded `explore-fake` stream replayed through both engines leaves identical snapshot bytes, the same graph time and the same commit log length).

| Case | Result |
|---|---|
| determinism (1000 property cases) | pass |
| glitch_freedom | pass |
| atomic_rollback | pass |
| time | pass |
| subscriber_order | pass |
| dynamic_dependencies | pass |
| equality_cutoff | pass |
| retention | pass |
| time_travel | pass |
| layering | pass |
| explain_and_metadata | pass |
| simulate | pass |
| hydrate_round_trip | pass |
| differential replay (mini vs causl) | pass |

My first straight host layer failed 3 of the 13. They are fixed now, but they are the useful finding, so here is each one with its cause:

1. **time_travel: engine gap.** `read_at` on a derived returned nothing useful. The engine only retains derived values when `State::retain_derived_rows` is switched on (it exists, it is off by default), and it keeps no seed for a derived, so a read before the node's first change is "evicted" even inside the window. I turn the flag on and keep each derived's registration value in the host as the fallback.
2. **retention: host layer bug.** The window was one short (`oldest_retained` 101 instead of 100). The engine's `commit_history_cap` counts retained states including time 0, the contract counts commits, so the cap is `COMMIT_HISTORY_CAP + 1`.
3. **determinism: engine gap.** A derived that picks up a new dependency during a recompute can land on a derived the engine has not recomputed yet (the engine orders the drain by the old edges), and it reads a stale value. The property test found a three-node chain that shows it. `mini` handles this by blocking and reordering. In the host I compute such a dependency on the spot ("pull"): if a read hits a derived that is not in the compute's previous dependency list and has a changed ancestor, I evaluate it first. The engine still recomputes it later in its own order, so a flipping node can run its compute twice in that one commit.

Not covered by the suite, so I did not test them: a dependency cycle (the host only has a recursion guard, no `CommitError::Cycle` from a real cycle check) and a compute reading a commit-metadata node.

## Stream commit, mini and causl side by side

Same fixture as A1.3 (`crates/aibus-core/benches/commit_stream.rs`, now generic over the backend and included by the causl bench so they cannot drift): 8 runs, 100k line transcript open, 2,000 log rows, 5,000 samples, release build. Microseconds, p50 / p99 / max.

| Where | Case | mini | causl |
|---|---|---|---|
| MARS (container, 1.85) | round-robin over 8 runs | 4 / 29 / 115 | 11 / 38 / 133 |
| MARS | open run only (worst case) | 21 / 29 / 128 | 29 / 38 / 132 |
| MARS | 48 KiB `Str` write (the spec's tail shape) | 12 / 25 | 50 / 64 |
| runner, run 1 | round-robin | 9 / 60 / 283 | 24 / 86 / 253 |
| runner, run 1 | open run only | 37 / 60 / 241 | 54 / 86 / 261 |
| runner, run 2 | round-robin | 7 / 44 / 170 | 19 / 60 / 285 |
| runner, run 2 | open run only | 30 / 44 / 182 | 43 / 60 / 199 |

The p99 on the round-robin row is the bench's combined p99 (the larger of the two cases), which is why it matches the open-run row. The budget is 4 ms p99, so causl is 45 to 100 times under it. After the measurement both engines end at graph time 13,940 with a 9,810 byte snapshot. The hosted runner is shared, so only the within-run comparison means anything: causl is roughly 1.3 to 3 times mini at p50, about 1.3 to 1.5 times at p99.

Where the extra goes I did not profile, but every changed value is encoded to JSON for the engine and decoded back for history reads, which is the obvious suspect. The 48 KiB tail as a `Str` is about four times slower than mini (and would still retain about 192 MiB over 4,096 commits on either engine), which is one more reason the tail stays a `Handle`.

## What the `unimplemented!()` traits cost

Less than I feared:

- **`Reader`:** nothing. `State::get_value` and `State::read_at_result` are public and are what I used.
- **`Observable`:** nothing. I did not need engine telemetry.
- **`Persister`:** I did not use it. `snapshot` and `hydrate` work on the typed inputs, the way `mini` does, which is also what makes the differential snapshots byte-identical. The engine's own `State` serde (including retained history) is therefore unused and unproven by this spike. If `Persister` lands upstream, it would only buy a faster full restore, not new behaviour.

The real costs are the three gaps above, the two-table slot hazard, and the JSON boxing of every value.

## Recommendation for C2.4

Go ahead with C2.4 as a second backend behind `causl-rs`, with `mini` staying the default (D-02 unchanged). The feasibility question is answered: the contract holds, the cost is small. Before the default could ever switch:

1. The crate has to be fetchable without a token. Until the mirror is populated or the source is vendored with a licence check, `causl-rs` can only be built by the workflow, and C2.4 work needs either that or a local path override. This is the blocker, not the engine.
2. Decide whether to upstream the three engine gaps (derived retention seed and default, dynamic dependency ordering) or keep the host workarounds. The pull workaround is the part I like least: it re-runs a compute and relies on a staleness check I wrote.
3. Keep the differential replay test and the conformance cases in CI for the causl crate, as the workflow does, and extend the replay fixtures as C2.4 adds messages.

## Not verified

- The hosted runs use the pinned commit; my local MARS runs used a checkout of another branch. I did not diff the two trees.
- No measurement on a 2020 laptop and no memory measurement of the causl backend over a 12-hour session.
- Cycle detection and metadata-dependency errors are not implemented or tested on causl (the suite does not cover them on mini either).
- `cargo audit` did not run (not installed here and in the workflow I only ran `cargo deny`, which covers the advisory database).
- The workflow cannot be started with `workflow_dispatch` until it exists on `main`; I ran it through a temporary push trigger on this branch, which I removed again before the PR. The final dispatch-only file has not itself been run.
