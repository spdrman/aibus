# A2.5 spike: the dashboard frame and its render cost

08 section 1 gives one dashboard render (view read, widget draw, ratatui diff) a budget of 3 ms p99. I rendered the frame from real `view:` deriveds and measured it on a `TestBackend`.

## The measurement

`crates/aibus-tui/benches/render_dashboard.rs`, release build, 5,000 samples per case, on MARS (i7-14700F) inside a container with the pinned 1.85 toolchain. Two timings per case:

- tick commit + redraw: `App::step(Msg::Tick)` (reduce, one commit, view recompute), `note_commit`, then `Ui::draw`. A tick moves the spinner of the running cards, so the draw is real and the diff small.
- resize redraw only: the backend is resized back and forth, so ratatui repaints the whole buffer. This is the worst case for the diff. It times `Ui::draw` alone (view read, draw, diff).

The "A1.3 fixture" is the commit_stream load rebuilt in `aibus_testkit::tui::heavy_app`: 8 runs, a 100,000-line transcript on the lead, 500 lines on every other run and 2,000 log rows, with all the `view:` nodes registered on top.

| Case | tick commit + redraw p50 / p99 | resize redraw only p50 / p99 |
|---|---|---|
| replay session, 98x46 | 106 us / 121 to 167 us | 131 to 132 us / 149 to 182 us |
| A1.3 fixture, 98x46 | 111 to 114 us / 122 to 142 us | 129 to 131 us / 142 to 157 us |
| A1.3 fixture, 80x24 | 66 to 67 us / 70 to 82 us | 67 to 68 us / 70 to 81 us |

Two runs of the final bench gave the ranges above (the host was shared). Four earlier runs of the draw-only variant had a worst p99 of 242 us. The budget is 3,000 us, so one render is about 15 to 20 times under it, and the worst single sample in any run was 787 us.

The 100k-line transcript costs the frame nothing: the dashboard never reads it, only the tail handle's version through the session log and cards.

## What I built

- `view:header`, `view:advisor_rail`, `view:lead_box`, `view:fork_layer`, `view:cards`, `view:return_box`, `view:session_log:lines`, `view:status_bar` and `view:dirty`. Each widget in `widgets.rs` takes one `&Value` and a `Theme`; it has no access to the graph. `view:dirty` is a commit-metadata derived that lists the widget names whose view node is in the commit's `changed_nodes`.
- `Ui::note_commit` looks at `view:dirty` once per new commit and remembers a pending draw; `Ui::draw` draws only when something is pending or the size changed. Doing it per commit (rather than reading `view:dirty` at draw time) means two commits between draws cannot lose the dirty one.
- Zero draws over 100 idle commits is `tests/dirty_and_draws.rs`; no `Msg::Tick` over 5 s is `tests/idle_no_tick.rs`.

## Deviations from 05

- **`Theme.dim_text` is new.** The sampled `dim` (#565f89) is 2.76:1 on `bg`, too faint for text, so `dim` is only for rules and travelling dots and `dim_text` (#8c96c2) carries dim text. All text pairs now clear 4.5:1 on `bg`, `panel` and `highlight` (lowest: `dim_text` on `highlight`, 4.80:1).
- **Two sampled colours stay below 3:1** and I did not change them: `dim` on `bg` (2.76:1, rules and dots, decorative) and `split_rest` on `panel` (2.06:1, the empty part of a split bar, whose value is also printed). C1 should decide whether to lighten them.
- **No cursor blink.** The prompt shows a static block cursor. A blinking one would keep `view:animating` true for an idle session, which contradicts "idle sessions render nothing" and `idle_no_tick`.
- **Card border never turns purple, and the return box and lead box highlight only from `CHECKPOINT_PENDING`.** The data to tell which card hit an error is not in the graph yet.
- **Lead box effort and flag** read `effort` and `model_flag` from the run meta when present and default to `high` and none; nothing writes them yet.
- **`model:router:last:<kind>` inputs are registered by `aibus_tui::register`** for the three fork kinds. The core registers them on the first answer, and a derived that read the key before that would never see it appear. First registration wins, so the core's own registration is a no-op afterwards.
- **`aibus-tui` runs its own channel and `Ticker`** in `app::run`, and does not call `App::run`, because that loop gives no hook to draw after a step. When the effects land in A2 they send to `App::sender()`; C1 will need `App` to expose the receive step (a small `run_with` hook) so the TUI loop can drain it.
- **ratatui 0.29, not 0.30.** 0.30 needs rustc 1.88 and the MSRV is 1.85. 0.29 pulls in `paste`, which `cargo deny` flags as unmaintained (RUSTSEC-2024-0436), so `deny.toml` ignores that one advisory with the reason. `instability` is pinned to 0.3.7 in `Cargo.lock` (0.3.14 needs 1.88).
- **No insta.** `assert_frame!` and `assert_styles!` compare against `tests/snapshots/<name>.txt` and `<name>.styles.txt`, and `AIBUS_UPDATE_SNAPSHOTS=1` rewrites them. It avoids a dependency tree for what is a string compare.

## Not verified

- The terminal loop in `app.rs` (raw mode, alternate screen, event thread, double `Ctrl+c`) never ran on a real tty. The tests cover the `Ctrl+c` window logic, key conversion and that the panic hook calls `restore`; the escape sequences themselves are untested.
- Only the recording palette exists. The `light` and `mono` themes, `NO_COLOR`, the 256-colour fallback and `[ui] ascii` are C1.
- Resize-to-re-layout under 10 ms is covered by the resize redraw numbers above (under 0.4 ms), not by a separate bench.
- No run on a slow machine and no debug-build timing.
