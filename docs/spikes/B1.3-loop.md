# B1.3: the run loop, command hooks, retries and budgets

Notes for whoever builds on the loop next (B2.1 delegate, B2.2 compaction, B2.4 resume, C2.1). Only what is not obvious from the code.

## Hooks

`HookRunner::fire(input, scoped_hooks, cancel)` is the only entry point. `[hooks]` run first, then the definition's, one after the other; the first block ends the chain. `HookRunner::default()` runs nothing, which is what `--no-hooks` builds (the startup step prints the warning).

* The run task fires `subagent_start` (workers), `user_prompt_submit` (a lead's first prompt and every mailed user message), `pre_tool_use`, `post_tool_use`, `post_tool_use_failure`, `pre_compact`, and `stop` (lead) or `subagent_stop` (worker). Startup fires `session_start` and `session_end`. `checkpoint` is only supported by the runner: the advisor (B2.x) is what fires it.
* A worker's `stop` in its definition is looked up for `subagent_stop`. A lead's `subagent_stop` does not pick up `stop`.
* Exit 0 with one JSON object is a verdict (`decision`, `reason`, `updated_input`). `deny` or `block` only counts on events that can block. `allow` changes nothing: a hook cannot lift the permission layer, only tighten it. `ask` makes the run raise the same `PermissionNeeded` the executor would, and the answer also answers the executor's own prompt, so the user is asked once.
* `updated_input` is applied before `ToolCallRequested`, so the graph and the transcript show what actually ran. It is not redacted (it is what runs); everything that goes back to the model is.
* Timeouts use tokio's clock (`sleep` next to the blocking thread), which is why a test can pause time. The flip side: a paused clock makes every hook time out at once, so tests that run real hooks must not use `FakeClock`.
* Capture is the last 1 MiB of each stream (the `Tail` that `bash` uses). Every run of a hook writes `logs/hooks/<session>/<event>-<ms>-<n>.log` through the redactor.
* The environment is `scrubbed_env`, shared with `bash`; `[hooks] pass_env` feeds both. `Config.hooks` is now `Hooks { pass_env, events }`, and an unknown event name is a config error with its line.

## Loop

* Retry: a retryable error waits 500 ms, 1 s, 2 s, 4 s, 8 s (so five retries and six requests at most), or the provider's `retry_after` if that is longer, never past 300 s. The card shows `retrying in N s (k/5)` through `StreamChunk::Waiting`, cleared before the next attempt. A retry after text already streamed repeats that text in the tail; I did not try to dedupe.
* `ContextTooLong` calls `RunDeps::compactor` once per request. With no compactor (B2.2 has not landed) it is a plain failure. `RunMail::Compact` does the same with trigger `manual`.
* `Auth` never retries. The message is the banner (`account <name>: <provider message>, run aibus account test <name>`), sent with `RunFailed` even when the run kept text, so the graph holds it. It maps to exit 5 through the run result, not 4.
* Budgets: checked after each response, and only when the run wants to go on (a final answer that overshoots is kept). Tokens are input plus output. Both end `Partial` with a `Budget` error, and the CLI maps that to exit 8; `max_turns` stays `Partial` with no error (exit 10). The unexecuted tool calls get an error result so the conversation can still be resumed.
* Cost per turn is the provider's own figure when it has one, otherwise the price table (it used to add both).
* `UsageUpdate` goes out after every turn with the run's absolute total.
* Mail is read at turn boundaries and once more when the model would stop, so a message that came in during the last turn gets an answer.

## Not done

* No compaction itself, no checkpoint firing, no `http` or `prompt` hooks.
* The effects sink for `Effect::Tool` is still idle; the run task executes tools itself.
* `Partial` with a provider error is exit 10, `Failed` with one is exit 5, whatever the error kind.
