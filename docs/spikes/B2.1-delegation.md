# B2.1: delegation, limits, background and foreground

Notes for whoever builds on this next (B2.2, B2.3, C1.2, C1.5). Only what is not obvious from the code.

## Who does what

* The graph decides what may start. `model:orchestrator:runnable` lists queued runs whose parent is alive, whose depth is within `max_spawn_depth`, while fewer than `max_concurrent_runs` are active, the run's account has a free slot (its own `rate.max_concurrent` from `model:limits.per_account`, else `max_per_account`) and fewer than `max_runs_per_session` have left the queue. `App::set_limits(&Limits)` writes `model:limits` at startup; `Limits::resolve` builds it from `[limits]`, the accounts and `AIBUS_MAX_SPAWN_DEPTH` / `AIBUS_MAX_CONCURRENT_RUNS`.
* `Orchestrator` (`orchestrator.rs`) is the runtime half. It holds the live runs (mailbox and cancel token), the foreground waiters and the roster. It is shared by the `delegate` tool, the effects executor and the tap that every child reports through.
* `Effects::orchestrated(orch, launcher, store, sink)` wires the executor. `Spawn` goes to `Effects::spawn_run`, which is idempotent by run id (a run that is live is left alone); `Cancel` and the new `Detach` go to the orchestrator; everything else still goes to `sink`. An executor made with `Effects::new` behaves as before (the sink gets `Spawn`).
* `Launcher` is the seam for building a child's `RunConfig` and `RunDeps`. The binary's is `ChildLauncher` (`crates/aibus/src/launch.rs`), which also builds the lead, so there is one place that turns a model and an account into a provider and a credential. A test passes its own with a fake per run.

## The `delegate` call

1. `Orchestrator::reserve` checks the limits and gives the run its id. The check counts active, queued and not-yet-visible requests, so two calls in one turn do not both get the last slot. The answer for a refused call is the tool result `{"error":"concurrent run limit reached (8)"}` (or `session run limit reached (500)`). Account slots are not checked here (the account is only settled when the run starts), so a run whose account is full waits in the queue instead.
2. The tool sends `Command::Delegate` with `run: Some(id)`, so the answer can carry the id before the loop has seen the command. Two commands with the same id queue one run.
3. Background (the default): the tool result is `{"run_id":"..."}` at once. When the child ends, the orchestrator puts the wrapped result (01 section 5.3) in the parent's mailbox as `RunMail::ChildFinished`, and the parent's loop appends it as a user message at its next turn boundary. It is a user message and not a tool result because the call already has its result; a second `tool_result` for one `tool_use` is not valid for the providers. A parent that is about to stop with such a message waiting goes round once more to answer it.
4. Foreground: the tool waits on a oneshot. The child's end answers it with the wrapped result. `Command::Background { run }` sets `background` in the run's meta, the executor reads that as `Effect::Detach`, and the wait ends with `{"run_id":"...","background":true}`; the result then arrives as in 3. A definition with `background: true` forces background in the tool and in the reducer. Cancelling the parent's call cancels the child.
5. `RunConfig::background` (the effective flag) strips `ask_user`, `enter_plan_mode` and `exit_plan_mode` from the run's tool list. `RunConfig::max_spawn_depth` is what removes `delegate` at the limit (`effective_tools` takes it as a parameter now).

## Orphans

A child whose parent ended is never started. The reducer cancels the queued runs below a parent when it finishes, fails or is cancelled while queued, and a delegate that names an ended parent is queued as `Cancelled`. `Orchestrator::start` also cancels (with `Command::Cancel`) a run whose parent is not live in the orchestrator, which covers a resumed snapshot.

## `@agent-<name>` and `--agent`

* `parse_mention` is the one parser. In the reducer, a `SubmitPrompt` that starts with a mention while a lead runs queues a background delegate with the lead as parent. In `aibus run`, a first prompt that starts with a mention sets `RunConfig::forced`: the run opens with a foreground `delegate` call to that agent in place of its first request (not counted as a turn), and then goes on with the result in hand.
* `aibus run --agent <name>` with no prompt sends the definition's `initial_prompt`; with a prompt, the initial prompt comes first and the prompt follows after a blank line. An unknown name (for `--agent` or a mention) is `AibusError::UnknownAgent`, exit 3.

## Not done

* `isolation: worktree` is in the schema and the command, and `ChildLauncher` refuses it ("not available yet"); the run ends `Failed` with that message.
* A lead that ends while a background child is still running does not wait for it; the report is lost with the session.
* `Command::Permission` does not reach a run's mailbox by itself. The surface that answers a prompt sends `RunMail::Permission` to `Orchestrator::mailbox(run)` (the test does).
* The roster follows `AgentsReloaded` in `aibus run` only; the TUI loop has to do the same (`set_roster` and `ChildLauncher::reload`).
* A child's `inherit` model is its parent's, from what `ChildLauncher` remembers; a reloaded definition does not change a run that is already going.
