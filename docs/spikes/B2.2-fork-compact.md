# B2.2: fork, resume, send_message, compaction and worktrees

Notes for whoever builds on this next (C1.3, C1.4). Only what is not obvious from the code.

## Two files per run

`runs/<id>/transcript.jsonl` is B2.4's display transcript (built from the `Msg`s, long results cut). A resume needs the messages exactly as the provider saw them, so the run task also writes `runs/<id>/conversation.jsonl` (`run::transcript`): `start` (agent, model, account, parent, depth, kind `run`, `fork` or `resume`), `system`, `message`, `extend` (blocks added to the last message, which is what a resume does when the file ends in a user turn) and `compact_boundary` (`pre_tokens` and the whole live context from then on). Every line goes through the redactor. The old transcript keeps its own `compact_boundary` line, written by B2.4 from `Msg::Compacted`. This deviates from the issue text ("reloads `transcript.jsonl`"), on purpose: two writers on one file would have corrupted it.

## Fork

* `fork` is background only. The tool reserves a run and sends `Command::Fork`; when the orchestrator starts it, it mails the parent `RunMail::Fork { reply }` and the parent answers with a copy of its conversation at its next turn boundary (or right before it ends). The task is added to that copy with `Conversation::push_user_text`, which joins the last user message as a block, so the fork's first request is the parent's messages word for word plus the task. A foreground fork would deadlock (the parent is inside the tool call), which is why there is none.
* The fork runs the parent's definition (`ChildLauncher::defs`, remembered per run), model and account. `fork` is taken out of its allow-list in the run task. Its tool list differs from the parent's by that one tool, so a provider that caches tools before the system prompt will not reuse the cache; the messages are still identical.
* `Command::Fork { prompt, parent, run }`: no parent means the lead (what `/fork <task>` does). The reducer marks the run's meta with `fork: true`.

## Resume

* `Command::Resume { run, message, parent }` re-queues a finished run under its own id. `SpawnSpec::resume` makes the orchestrator set `RunConfig::start = Start::Resume`, and the run task loads `conversation.jsonl`, adds the message and goes on. Budgets and turn counts start again from zero, which is what makes a `Partial` run worth resuming.
* A history that ends in an assistant message with unanswered `tool_use` blocks gets error results first (`push_user_text`).
* `resume_run` takes an id or an agent name (the latest run of that agent, from `Orchestrator::resolve`). `send_message` on a run that is not live errors with a pointer to `resume_run`.
* `aibus session resume <id> --run <run> "<msg>"` is a headless `aibus run` with `RunArgs::resume` set: same session directory and `session.json`, the run's own definition, model and account from the `start` line. Without `--run` B2.4's hydrate-and-report is unchanged. `--script` on that subcommand is hidden and exists for tests.
* `Command::SendMessage` still only logs. The control channel and the tool deliver to the mailbox directly.

## Compaction

* Order in `Task::compact`: `pre_compact` hooks, `Compactor::handoff` (lead only; the default writes nothing, C-side handoffs plug in there and `HandoffWritten` is sent when it returns a path), the summary, the `compact_boundary` line, `Msg::Compacted`.
* `ModelCompactor` (`run/compact.rs`) summarises with the run's own provider and model. It sends the conversation flattened to text in one user message with no tools (a provider rejects `tool_use` blocks without tool definitions), cutting from the front when the text would not fit half the window. The summary replaces the whole history as one user message.
* Triggers: `RunMail::Compact` (`/compact`, `Command::Compact` through `Effect::Compact`), `auto_compact_at` or 80 % of the model's window when the last response's input tokens reach it (before there is a response, the heuristic estimate with its 10 % margin), and `ContextTooLong` once per request. Auto only runs when a compactor is set. A failed compaction is an `IoError` with context `compacting <run>`, which also takes the run out of `compacting`.

## Worktrees

* `worktree::create` makes a detached checkout of the default branch (origin/HEAD, else `main`, `master`, HEAD) at `<cache>/worktrees/<session>/<run>`, with `cwd` keeping the project's place inside the repository. `release` removes it when clean, keeps it when there are changes, untracked files or commits no branch has. `sweep` does that for everything left at session end.
* `ChildLauncher` creates it for `isolation: worktree` from the call or the definition (`audit` has it), sets the run's `cwd`, and the run task releases it in `finish`; a kept one comes back as `RunResult::worktree`. A resumed isolated run reuses the kept checkout.
* `delegate` asks (`Need::Ask`) when the call or the target definition is isolated, so `default`, `accept_edits` and `dont_ask` follow the 09 table.
* The lead's own run is never isolated; `doctor` already listed kept worktrees.

## Not done

* The TUI has no input line yet, so `/fork` and `/compact` are parsed in the reducer (`SubmitPrompt` while a lead exists), not in a widget.
* `RunResult::worktree` is not in the `RunFinished` NDJSON event; the schema has no field for it.
* A fork that was asked for just as its parent ends is refused ("the run to fork from ended first") unless the parent was already waiting for mail.
