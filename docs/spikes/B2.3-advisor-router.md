# B2.3: the advisor and the router

Notes for whoever builds on this next (C1.2, C2.2). Only what is not obvious from the code.

## Where things live

* `advisor.rs`: `Triggers` (the checkpoint state machine over the lead's events), `normalise_error`, and `Ledger` (every run's compacted transcript, `Ledger::packet` elides it to `packet_max_tokens`).
* `router.rs`: `ask` (one 16-token completion), the answer parser, `p` from logprobs, and the helpers the three sites use (`ends_with_intention`, `which_file_candidates`, `read_head`).
* `assist.rs`: `Assist` is what `RunDeps::assist` holds: the advisor seat, the router seat, the ledger and the fork counter. `ChildLauncher::set_assist` builds it at startup and every run launched afterwards shares it.
* `run/loop_/assist.rs`: `LeadAssist`, the lead's side. The main loop calls it at five points (before a request, after the reply, after the tool results, on a failed call, when the turn would end). A run that is not the lead only keeps the ledger.

## How a checkpoint goes

1. `Triggers` fires on the lead's event (reply, tool result, turn end). The `checkpoint` hook runs; exit 2 skips the advisor and `HookFired` is logged as "advisor skipped".
2. `CheckpointHit` sets `active_checkpoint`, so `model:checkpoint:pending` is the checkpoint name and `Effects` emits one `Effect::Advise` for it. The lead's own task makes the call, because it has to finish before the lead's next request. The effect is a signal for other surfaces and is ignored by the headless sink.
3. The advisor runs on its own seat with its read-only tools (`effective_tools` for `Role::Advisor`: read, glob, grep, ls, whatever its definition lists), at most four rounds. `AdvisorSpoke` clears the pending key and adds to `calls` and `tokens_read`. A failed call sends `IoError` and an empty `AdvisorSpoke`, so the pending key is never left set.
4. The advice waits as `[advisor] <advice>` and goes in as a `System` message before the lead's next request. A turn that ended with no tool call goes round once more to read it.

Judgement calls: `same_error_x2` clears after it fires (three equal failures fire once, four fire twice). `before_done` fires again only when more workers have completed since it last fired, which is what stops a lead that keeps ending from being advised forever. Custom checkpoints (`on: tool_result`) match their `matcher` regex against the tool name or the result text. Only the lead's events are watched. Advisor and router calls are not added to the run's usage or budgets.

## The router

* `RouterQuestion { kind, context, choices }` and `RouterAnswer { choice, p, verdict, latency }` are as in the spec; `RouterAnswer` also has `source` (`Logprob` or `SelfReport`, Q4), kept in `model:router:last:<kind>` with `latency_ms`. `Verdict::Soft` is gone (the spec has sharp and split).
* `p` is the product of the logprobs of the tokens that spell the choice when the provider streams them, else the `p` the model wrote, else 0 (so split). `ChildLauncher` asks for a logprob-capable account for the router (`SelectHints::logprobs`).
* Sites: `which_file` before a request when the newest message names a symbol that more than one file has (grep over the project, at most eight candidates), `retry_or_stop` after a tool failure that was not a refusal, `which_tool` when the lead ends on an intention. Sharp `retry_or_stop` retries once (a denied retry keeps the first error) or ends the run `Partial` with a `Tool` error; sharp `switch tool` and every split leave a `System` note. `which_tool` asks once per stop, and sharp pre-fills `tool_choice` for the next request.
* `max_per_turn` counts questions between two requests. A question that fails (provider error, answer outside the choices) sends `IoError` and the lead carries on as if the router were off.
* Latency: each question is a `router` span in the `--trace` file with `latency_ms` and `turn_ms` (the sum so far in the turn), for the Q3 measurement. The trace viewer has a `router` track.
* `router.label` names the router in its notes (`[jev] ...`); the panel title is the TUI's to read from config.

## Startup

`--advisor` / `--router` take a model or `off`; `[advisor].enabled` and `[router].enabled` turn them off in config. Each off case prints `aibus: note: the advisor is off: <why>` on stderr. With no flag and no config the alias is `opus` for the advisor and `fast` for the router (Q6); with no accounts at all (the built-in fake) nobody is consulted unless a flag names a model, so a fresh install says nothing.

## Not done

* The definition's `router.questions` (custom kinds) are not asked anywhere; `RouterKind::Custom` exists for them.
* The advisor has no delta mode (Q5 says it is a later option).
* Workers' failures do not trigger `same_error_x2`; the recording shows the failing worker's card lighting up, which needs the worker's events routed to the lead.
