# B2.4: persistence, resume, retention

Notes for whoever builds on this next (C1.3, C1.4, C2.3, C2.4). Only what is not obvious from the code.

## What is written, and by whom

* `SessionWriter` (core, `persist::session`) is the one writer of a session directory. `aibus run` builds it in the graph step, feeds it every `Msg` the lead run sends (`writer.msg`) and calls `writer.after_step(app)` after each `App::step`. `OpenSession::stop` calls `finish`, which takes the last snapshot.
* `App::record_commits()` turns on a journal: every commit that changed an input is kept (key and value) until `take_journal`. That is what `commits.jsonl.zst` is written from. A `Commit` alone names nodes by index, so it could not rebuild anything, which is why a log line is `{time, intent, changed: [[key, value]], at}` and not a `Commit`.
* Snapshot first, then `Msg::Persisted`: the snapshot is taken before the `Persisted` commit, so that commit is always the first line after it in the log. `session resume` replays only lines with `time` greater than the snapshot's `now`.
* Log and message files are written as one zstd frame per 100 lines or 2 s (concatenated frames are valid zstd), so a crash loses at most the unflushed lines and a cut frame at the end is ignored on read.
* `msgs.jsonl.zst` holds the messages `replay::msg_to_json` knows (what a run task sends). Other messages (`HookFired`, `Compacted`, ...) are not in it, because `replay` cannot decode them yet. They do reach the transcript.

## Resume

* `session::load` reads the snapshot, runs `migrate::chain(version_of(snap), snap)` and returns the commits after it. `App::hydrate(snap, tail)` registers the run keys, hydrates, applies the tail, then runs `after_commit` once.
* `SCHEMA` is 1, so `STEPS` is empty. The first change to the node set adds `STEPS[0]`, bumps `SCHEMA`, and runs `write_the_fixture_for_the_current_schema` with `--ignored` to add `fixtures/snapshots/v2/`. `every_fixture_migrates_and_hydrates` fails until each version has a file.
* `aibus session resume <id>` hydrates into a fresh graph and reports. It cannot continue a run yet (no live loop outside `aibus run`), so `--run` or a message exits 2 after hydrating. The effects sink is still idle, so queued work does not restart until something executes effects.
* Handles in a snapshot point at the side store, which is empty after a resume. Rebuilding blocks from the transcripts (03 section 9) is not done: nothing draws a resumed session yet.

## Index

* `index.sqlite` lives in the data dir, is opened only by `session list|show` and at session end, and is rebuilt when it is missing or its session count disagrees with the directories. `memory_fts` and `memory_files` exist but nothing fills them (memory indexing is a later task).
* `session show` takes `handoff` and `ledger` from the last snapshot (`model:handoff:latest`, `model:ledger`).

## Retention

* Session age is read from the ULID in the directory name, not from a file date, so a copied or touched directory keeps its age.
* `prune` also expires `cache/models/*.json` after 7 days. Nothing writes that cache yet.
* The log is a small rotating writer in core, not `tracing-appender`: that one makes files with the default mode, and the log has to stay `0600`.

## Two processes

* `fs::write_locked` is the `fs4` helper for ledgers and handoffs (held for one write). Nothing calls it yet, because the ledger and handoff writers are later tasks; the test hammers it from two threads.
* The handoff watcher reuses `agent_watch::start` with `RecursiveMode::Recursive` and sends `Msg::HandoffWritten` for the newest name. It only watches a directory that exists when the session starts.
