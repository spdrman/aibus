# B2.5: the command line, diagnostics and the trace

Notes for whoever builds on the CLI next (C1.1 workflows, C2.2). Only what is not obvious from the code.

## `aibus run`

* Without `--json` it is plain mode: the lead's text streams to stdout, tool calls are one-line `aibus: tool <name> <path or command>` notices on stderr, and the run ends with a status line (`aibus: completed, 2 turns, 400 in / 60 out tokens, $0.0012`). `--json` is NDJSON as before. Every test that parses events passes `--json` now.
* `events::Events` is the one place a `Msg` becomes an event. It remembers each tool input so `PermissionNeeded` can carry `input`, replaces an input bigger than `limits.result_max_bytes` with `{"truncated":true,"bytes":N}`, and splits a streamed text longer than the cap into several `Stream` events (nothing is lost). Messages the spec does not list still print their redacted summary under their own `type`.
* The control channel exists when `--json` is set, the prompt is on the command line (not `-` and not piped) and stdin is not a terminal. It then also turns on `Gate.tty`, so a prompt in `default` mode waits for a `Permission` line. When stdin closes, every open prompt and every later one is denied with reason `"no tty"`, so a run cannot hang on a dead pipe.
* `SendMessage` is mailed to the lead as `RunMail::UserMessage`; a `run` that is not the lead is reported on stderr and dropped. Bad lines are reported on stderr as `aibus: control: <why>` and do not stop the session.
* SIGWINCH sends `Msg::Resize` with the size from `term::size()` (80x24 without a terminal). In `--json` mode it shows up as a `Resize` event.
* `session.json` now also holds `ended`, `runs` (id, agent, status, turns, usage) and `handoff_outcome` (`--outcome`, else `AIBUS_OUTCOME`, canonical upper case). `commits.jsonl` next to it is the commit log `session log` prints.

## Exit codes

* `RunErrorKind::Auth` is new. The loop marks a provider auth failure with it, and the CLI maps it to exit 4 (`CredentialError::RunRejected` carries the banner), also when the run kept some text. Before, it was 5 through `Provider`.
* Partial plus Budget stays 8 and `max_turns` stays 10. `Partial` with any other provider error stays 10.
* 11 is `doctor`, 12 is `agent validate`. 9 is still unassigned.

## Logging and the trace

* `aibus.log` is written by `logfile::RotatingLog`: the active file is always `aibus.log`, a rotated one is `aibus.log.<YYYY-MM-DD>` (`.1`, `.2` for a second one in the same day), `log_files_kept` counts the active file, and the size guard rotates at 64 MiB. I did not use `tracing-appender` (07 section 4 names it) because it has no size guard and its file naming cannot be told to keep the active name stable; the writer is about 100 lines and tested with a fake clock.
* `AIBUS_LOG` is a comma list on top of what `-q`, `-v`, `-vv` set: `debug` moves the default, `aibus_core=debug` adds a target. A directive that does not parse is noted in the log file once.
* The engine's spans use target `aibus_trace` (`commit`, `effect`, `provider_call`, `tool_call`, `hook`). The log filter turns that target off, and the Chrome trace layer only exists with `--trace`, so without it every span is a disabled callsite. The file is the JSON object form and is flushed per event; `chrome://tracing` and Perfetto read it, though I could only check the structure here, not open it in either viewer.

## Not done

* `session resume | export | replay | prune`, `handoff`, `ledger`, `memory` and `workflow run` are still "not yet" (exit 2). `handoff` and `memory recall` have schemas in `docs/schemas/cli/` but no command to test them against.
* `doctor --session` prints `memory.json` from the session directory if it exists; C2.3 is what writes it.
* The zsh, fish and PowerShell completion scripts are generated and checked for their content, but only the bash one is loaded into a real shell in the tests.
