# C1.2: the dashboard widgets and the mouse

Notes for whoever builds on the dashboard next (C1.3, C2.3). Only what is not obvious from the code.

## What is where

* `aibus-tui/src/view.rs`: every `view:` node. New since C1.1: `view:delegate_row`, `view:run_tips` (what a tooltip says about each run) and `view:menu` (the open context menu with the items that apply). `shown_workers` is the one place that decides which workers have a card; the reducer's `visible_workers` follows the same rule, so `ctrl:selected:card` means the same run on both sides.
* `aibus-tui/src/widgets.rs`: one function per panel, plus `menu` and `tooltip`. Widgets still see nothing but a `Value` and a theme. `padded` is a panel with a blank column each side, as the recorded boxes have; the rail pads on the left only, because `» plan skips auth` needs the 17 columns.
* `aibus-tui/src/ui.rs`: `centre` lays out the column and draws the dotted paths (`dotted` only draws on blank cells, so a path never cuts through a box), `advisor_link` joins the active checkpoint to its box, `render` builds the hit map and puts the menu or the tooltip on top. `Chrome` now carries `tick`, the log filter and follow flag, and whether a menu is open.
* `aibus-tui/src/input.rs`: right click, the menu keys, the tooltip clock. `Input::settle(now)` decides which tooltip is up; `Input::tip_due(now)` is how long the loop may sleep before it has to look again. Tests pass their own `Instant`s.
* `aibus-core`: `UiIntent` gained `ToggleFollow`, `OpenMenu`, `CloseMenu`, `MenuSelect` and `Mem`; `Command::LogFilter(String)`; inputs `ctrl:log:follow`, `ctrl:menu`, `ctrl:mem`, `model:session:model_flag` and `model:session:assist`; `advice_tick` in `model:advisor:state`; log rows now carry `actor`, `run` and, for the router, `p` and `verdict`. `App::set_session_view` writes the startup labels in one commit.

## The lead run from a TUI session

`startup::interactive_steps` now includes `EnterLoop`. In a TUI session it wires the orchestrator, the launcher and `Effects::orchestrated` into the app and builds no lead plan. A prompt sent from the input line reaches the reducer as `SubmitPrompt`; with no runs it queues the lead, `model:orchestrator:runnable` lists it, the effects hand it to `ChildLauncher::launch`, and it starts like any other run. `aibus-core/tests/lead_from_prompt.rs` covers the seam with a recording launcher. `tui::drive` passes the orchestrator's channel to the loop (`Options::msgs`) and a `watch` hook that keeps the roster and the launcher's definitions current on `AgentsReloaded`.

Not wired: `session_start` and `session_end` hooks, the session writer (no `state/sessions` files yet from a TUI session), and permission prompts. The gate runs with `tty: false` in a TUI session, so a tool that would ask is refused as "no tty" until the permission modal exists (C1.3). A lead that cannot be built (no key for the account) fails as a run and shows in the log, instead of exiting 4 at startup like `aibus run`.

## Deviations and judgment calls

* **`m` is the context menu, so "message the run" moved to `M`.** 05 section 4 has `m` for `send_message` and 05 section 6.1 has `m` for the menu; the issue asks for the menu on `m`. The message key was a no-op until now.
* **The ledger shows from 100 columns, not 110.** C1.1 already chose 100 (05 section 6) and this keeps it. To make it fit I narrowed the gaps between the four segments to 3 columns from 100 up (they stay 6 wide below, as in the recording). At 110 the ledger gets about 40 columns.
* **The `same_error_x2` card is the newest failed worker.** The checkpoint carries no run id yet (B2.3: only the lead's failures trigger it), so the purple border goes to the newest worker that failed or has an error, and to none if there is none. The rail's connector then points at nothing.
* **The advisor's subtitle says `advising` while the advice is typed out**, not between the call and the next checkpoint, and the status bar follows it. The diamond is only filled while the checkpoint is pending (`reading`).
* **A result is "in flight" for 3 seconds after a worker ends**, while the lead is still going. That is what makes the return arrowhead pulse. There is no mailbox signal for it in the graph.
* **Fork and Resume in the menu are blunt.** Fork queues a fork of the run with the prompt `continue the work of run <id>`; Resume sends `continue`. A real prompt needs the input line, which comes with the slash commands. Copy result copies the last block of the run's transcript (or what is still being written).
* **No tabs or breadcrumbs exist yet**, so those two clickable things from 05 section 6.1 have nothing to be clicked on. The ledger segment opens its tooltip (the whole line) instead of a screen, and the permission alert is a hit region with no action until the modal is there.
* **A dismissed or replaced card is hidden, not deleted.** `x` on a finished run sets `dismissed` in its meta; a finished card also gives way to a later run of the same agent. The run stays in the graph and its log rows still open its transcript.
* **`ui.log_rows` is applied once at startup**, as a log box of `log_rows + 2` rows, unless a dragged size is saved in `state/ui.toml`. Under 3 rows it is 3.
* **Replay hash.** The new `ctrl:` and `model:session:` inputs and `advice_tick` are part of the graph hash, so `tests/replay/explore-fake/snapshot.hash` changed (`c4193504b533425a` to `4e43d5e356de4ed6`).
* **Memory under `-v`** is read from `/proc/self/statm` (4 KiB pages assumed) or, off Linux, from `ps`, every 2 seconds, and only while `-v` is given.
