# C1.4: ledger, handoffs, memory, recall and learnings

Notes for whoever builds on this next (C1.5, C2.1). Only what is not obvious from the code.

## Where things live

* `aibus_core::continuity` holds the files and the rules: `Layout` (project, `thoughts/`, data dir, topic, scopes), `ledger`, `handoff`, `memory`, `recall` and `learn`. `aibus/src/continuity.rs` is the two ends of a session (start and end), `continuity_cmd.rs` the `ledger`, `handoff` and `memory` commands.
* The project root is `project_root(cwd)` (the nearest `.aibus` or `.git`), not the cwd, so `thoughts/` and `.aibus/agent-memory*` sit at the root of the repository wherever aibus was started.
* The topic is `--topic`, else the git branch with `continuity.topic = "branch"`, else the newest `CONTINUITY_<topic>.md` by mtime, else `general`. It is fixed for the session when it starts, so a ledger another process touches later does not move it.

## Ledger

* `Ledger::parse` keeps a section it does not know (a person added `## Notes`), and `render` writes the five known ones first if they were missing. In every section but `Goal` each line is a list item, so "the first In Progress item" means something. `ledger_update` and `aibus ledger update` replace a section, or add to it with `append`.
* `ledger_update` also steps `Command::LedgerUpdate` for `goal` and `in_progress`, which is what `model:ledger` (the status bar) holds. The reducer only knows those two plus `now`; the other sections are in the file only. At `session_start` the same two are stepped from the file.
* Writes go through `persist::fs::update_locked` (read, change, write under one `fs4` lock) and reads through `read_locked`, so two terminals do not lose each other's lines.

## Handoffs

* A `Handoff` is the ordered YAML mapping as it was read, not a struct, so keys this version does not know survive a round trip. `parse` accepts the two-document form (front matter, then body) and a single document; `to_yaml` always writes the first. `goal` and `now` are the only required keys.
* The schema's own example has `test: cargo test -p server auth::`, which strict YAML rejects (the trailing colon). `parse` retries with plain values that hold `: ` or end in `:` quoted, so that example, which is `fixtures/handoffs/auth-refactor.yaml` verbatim, parses unchanged. The other samples in `fixtures/handoffs/` are my own, written to the schema in 01 section 8.2 (there was no real Continuous-Claude export to copy from).
* `auto-handoff-<ts>.yaml` would sort after every dated name, so "the newest name wins" compares the name without the `auto-handoff-` prefix. `handoff::latest` and `list` do that; nothing else should sort handoff names.
* The auto-handoff at `pre_compact` (`ModelCompactor::handoff`) and the one at `session_end` ask nothing of the model: `goal` and `now` are the ledger's Goal and first In Progress item, falling back to the conversation's first user line and last assistant line. `create_handoff` and `aibus handoff create` take them from the caller. All three go through `Handoff::build`.
* `session_end` writes a handoff when `continuity.handoff_on_end` is on and the ledger's hash differs from the one taken at `session_start`. Its status comes from how the lead ended (complete, blocked, partial) and its outcome from `--outcome` or `AIBUS_OUTCOME`.
* `SessionEnd`'s `handoff` is that file relative to the project, or null.
* The lead is shown the newest handoff of its topic and the ledger as the first blocks of its first message (`RunConfig::context`), not as a separate system message. Workers get neither (Q24). A resumed run gets neither, since it has its conversation.

## Memory and recall

* `memory_dir` is shared by the first message (`MEMORY.md`) and `ToolCx::memory`, which the `memory_*` tools are rooted at. `confine` refuses absolute paths, `..` and symlinks that lead out, whether or not the file exists yet.
* There is no `aibus init` command yet, so `.aibus/agent-memory-local/` is added to `.gitignore` the first time the local scope is written to (`memory_write`, `memory_append`, `memory add --scope local`).
* `MemoryIndex` is implemented by `persist::index::Index`, one FTS5 row per file. `sync` reads a file only when its mtime moved, and re-indexes it only when its FNV-1a hash moved too (`content_hash`, stable across Rust versions). `index.sqlite` is shared by every project, so `sync` and `recall` only touch rows that are user scope or under the project's path, and only for the configured scopes.
* A query is split into words, each quoted, and any of them may match; bm25 ranks, and the score printed is its negation (higher is better).
* The `recall` tool syncs before it searches, so a file written a moment ago is found.

## Learnings

* Extraction is one call to the lead's own provider and model in a fresh context (`ModelCompactor::extract`, which reuses the compaction text flattening). It runs only when `memory.extract_on_end` and `continuity.extract_learnings` are on, a run of the session completed, the session was not interrupted (which is what `q!` and a second signal come to here), and the lead's `conversation.jsonl` loads. It has a 60 s limit; a failure is a warning.
* The reply is parsed leniently: the first JSON array in it, up to ten elements, each with a known `type` and `confidence` and some `content`. Entries go to `agent-memory/lead/LEARNINGS.md` in the user's data dir under `## <date> session <id>`, scrubbed by the redactor.
