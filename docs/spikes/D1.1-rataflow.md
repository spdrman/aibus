# D1.1: rataflow behind a feature, and what it costs

Notes for the go or no-go on phase 2 of the rataflow epic (#85). I wrote the plumbing and read rataflow 0.1.0's source end to end; The first pass did not run the measurements below, because the owner rule for that wave was that suites, benches and release builds run once, on the release PR. #91 ran 1 to 5 for real, in docker on MARS (`rust:1.89-bookworm`, `CARGO_TARGET_DIR=/tmp/target`, 28 cores shared with other jobs, load average 19 to 28 while they ran), and the cells are filled below. The two questions a read of the source can answer (6 and 7) are answered with the lines I read.

## What is in

* `aibus-tui` has a `flow-diagram` feature (off by default) that turns on `rataflow = { version = "0.1", optional = true, default-features = false, features = ["crossterm"] }`. The `aibus` binary forwards it. `release.yml` builds defaults, so a release binary does not contain rataflow.
* `src/diagram.rs` is the only file that names `rataflow`. `ui::centre` has one branch: with the feature on it calls `diagram::centre`, which has the same signature and returns the same `Centre`, so the hit map, the rings and the advisor link are untouched.
* Every frame `diagram::centre` builds a fresh locked `Flow`: nodes `lead`, `fork`, `card:<i>`, `return` at the rects the classic code computes (world cell = screen cell, zoom 1, no pan), a `NodeContent` that fills its scratch buffer with the theme's `bg`/`fg` and then calls `widgets::lead_box`, `fork_layer`, `card` and `return_box`, and `StepEdge` edges lead to fork, fork to each card, first card to return. Hidden handles, nothing draggable, selectable, connectable or deletable.
* To call a card box on its own I split `widgets::cards` into `card_rects`, `card` and `card_counts`. `cards` is now those three in a row and draws the same cells.
* The delegate label and the `+N more` counters are not nodes: they are not boxes, so they are drawn straight on the frame before the flow renders.

Dependency cost, from the lock: one new package. `rataflow 0.1.0` depends on `ratatui` and `thiserror 2`, both already in the tree. With `default-features = false` there is no `rust-sugiyama`, `petgraph`, `fixedbitset` or `log`, and no `serde`, `termion`, `termwiz` or `ratzilla`. Two tests in `aibus-testkit/tests/workspace.rs` pin that. rataflow is edition 2024 with `rust-version = "1.88"`, under our 1.89 MSRV. Licence: MIT, already on the allow-list.

### 6. Themes

`diagram::palette(&Theme)` copies our tokens into rataflow's eight-colour `Palette` (`canvas_bg` bg, `surface` panel, `muted` dim_text, `subtle` dim, `accent` focus, `text` fg, `success` ok, `error` error) and the flow gets `Theme::Custom(palette)`. Nothing in rataflow's built-in node, edge or canvas code names a `Color` literal outside its own `Palette::DARK` and `LIGHT` constants and its tests; every colour it paints comes from `flow.theme.palette()`. So with a custom palette no colour of its own leaks through. In the mono theme every token is `Color::Reset` and rataflow passes `Reset` through untouched (a test pins the mono palette to all `Reset`).

`muted` takes `dim_text` rather than `dim` on purpose: `dim` is the sampled rule colour and is 2.76:1 on `bg` in the recording theme, which is under the 3:1 an edge needs. The palette pairs, measured: recording muted 5.91 on bg and 5.60 on panel, accent 9.96 and 9.44, text 10.59 and 10.03; light muted 6.95 and 7.63, accent 6.11 and 6.70, text 15.58 and 17.09. All clear 3:1 (the test prints them).

ASCII: no. `StepEdge` draws `─ │ ╭ ╮ ╰ ╯` and an arrow marker and knows nothing about `theme.ascii`. `EdgeStyle::ascii()` exists, but it is a style the caller has to pick, and `Theme::g` is how every other glyph here falls back. The frame sweep (`glyphs::sweep`) would still map the box-drawing cells to ASCII at the end of the frame, but a dedicated `EdgeContent` that asks `Theme::g` is the right fix, and it is what the next issue builds (the `Dotted` edge), because the dotted look needs one anyway.

### 7. Locked behaviour

With `with_locked(true)`, `handle_mouse_event` (event_handlers.rs) takes a shortcut before any hit test:

* Left down starts a pan (`DragState::Panning`) and returns. No hit test, so `NodeClicked` is not emitted.
* Right down goes to `on_right_down`, which does hit test and holds a `NodeContextMenu` (or `PaneContextMenu`) event until the button comes up. So `NodeContextMenu` is still emitted when locked; `NodeClicked` is not.
* The wheel still zooms, locked or not (`zoom_around`).

That answers the question the next two issues depend on: I cannot lean on `NodeClicked` from a locked flow, and I must never forward a wheel event to it. Both are fine, because the hit map resolves clicks and menus before anything else (it already does), and a pan can be done by moving the viewport myself (`Flow::pan`, or just building the next frame's viewport from `cards_x`). The plan for phase 2 is therefore not to forward any mouse event to the flow at all.

## Recommendation

Go. Measurements 2 and 3 came back inside the budget (#91): p99 at most 0.33 ms against 3 ms and 10 ms, and one hash per size over 200 renders. Reasons:

* The cost in the tree is one small crate with two dependencies we already have, off by default, behind one file. If it goes wrong, deleting `diagram.rs`, the feature and one `cfg` line removes it.
* Everything risky about rataflow's input model (zoom on the wheel, left drag that moves nodes) is avoidable because I never hand it an event.
* What it earns is the pan canvas for more than three cards (#89), which the hand-drawn code would need a lot of new layout for.

What would have flipped it to no-go: a p99 over 3 ms at 98x46 (building a `Flow` per frame allocates a few small maps), a hash that differs between renders, or a snapshot diff in the boxes themselves in the next issue. In the first case the answer is to keep a `Flow` between frames instead of rebuilding it; in the other two I would stop.
